# Быстрый запуск: `docker compose` и `reviewbot init`

Статус: проект, ничего не реализовано. Нужны решения по пунктам из раздела «Открытые вопросы».

## Проблема

Сейчас запуск — семь шагов в README: три токена, ручной `config.yaml`, сборка образа
песочницы, `docker compose up -d egress`, переменные окружения, подключение репозиториев.
Ошибки видны только после первого MR: нет роли у бот-аккаунта, не тот scope у токена,
GitLab не достаёт до вебхука, не собран образ песочницы.

## Цель

Человек с токенами GitLab и Claude доходит до первого ревью за 5–10 минут и до первого MR
узнаёт, что настроено неверно.

Не цель: мастер для всех ключей конфигурации (их сотни, `docs/configuration.md`), графический
установщик, управление бот-аккаунтом в GitLab.

## Варианты

| | A. `reviewbot init` + compose | B. мастер в вебе при первом запуске | C. только compose с `.env` |
|---|---|---|---|
| Что делает | опрашивает в терминале, проверяет токены, пишет `config.yaml` и `.env`, предлагает запустить compose | бот без конфига поднимает `/setup`, форма пишет конфиг на диск | `cp .env.example .env`, править руками, `docker compose up` |
| Секреты | вводятся в локальном терминале, лежат в `.env` с правами 600 | уходят по HTTP на ещё не защищённый сервис | в `.env` руками |
| Проверка до запуска | да, `reviewbot doctor` | да, но уже на запущенном боте | нет |
| Работает без UI/браузера | да | нет | да |
| Риск | низкий | высокий: неавторизованный сервис принимает токены и пишет конфиг | низкий, но ошибки находятся поздно |

## Рекомендация

**A как основной путь, C как его результат, B не делать как «запись» — только как чтение.**

1. `docker compose up` с готовым `.env` — единственный способ запуска «из коробки».
   В репозитории уже есть профиль `full` (`docker-compose.yml`): бот, egress-прокси, сеть
   песочницы. Добавить `.env.example` и опубликованный образ (см. открытые вопросы).
2. `reviewbot init` готовит `config.yaml` и `.env` и проверяет их. Он же отвечает за
   образ песочницы и пересборку.
3. `reviewbot doctor` повторяет те же проверки на живой конфигурации. Те же результаты
   показывает страница `/setup` (только чтение, за той же защитой, что остальные страницы).
   Запись конфигурации из веба не делаем: сервис принимал бы секреты до того, как настроен.

## `reviewbot init`: сценарий

Интерактивный режим по умолчанию. Для CI и автоматизации те же значения через флаги и
переменные окружения (`--non-interactive`, ничего не спрашивает, при нехватке данных выходит с ошибкой).

```
$ reviewbot init

1/6  GitLab
     Адрес [https://gitlab.example.com]:
     Группы (через запятую) [backend]:

2/6  Токен бот-аккаунта (GITLAB_TOKEN, ввод скрыт):
     ✓ пользователь reviewbot, scope api
     ✓ роль Reporter в backend (нужна ровно эта, не выше)

3/6  Служебный токен (GITLAB_SERVICE_TOKEN, Enter — пропустить):
     ✓ scope api, роль Maintainer в backend
     без него бот не закрывает треды, не назначает ревьюера, не создаёт вебхуки

4/6  Claude
     Способ: [1] claude setup-token  [2] ANTHROPIC_API_KEY
     ✓ токен принят (формат), живая проверка делается на первом ревью

5/6  Как GitLab сообщает о MR
     [1] вебхуки   [2] опрос API (если до бота не достучаться)
     Публичный адрес вебхука [https://reviewbot.internal/webhook]:
     ✓ секрет вебхука сгенерирован

6/6  Песочница
     ✓ docker доступен
     ✗ образ reviewbot-sandbox:latest не найден   → собрать сейчас? [Y/n]

Записано: config.yaml (без секретов), .env (права 600)
Запустить сейчас: docker compose --profile full up -d  [Y/n]
Дальше: добавьте .reviewbot.yaml в репозитории (reviewbot init --repo-config > .reviewbot.yaml)
```

### Что проверяет (общее для `init` и `doctor`)

| Проверка | Как | Ошибка говорит |
|---|---|---|
| адрес GitLab | `GET /api/v4/version` | недоступен, неверный TLS, прокси |
| токен бота | `GET /user`, `GET /personal_access_tokens/self` | нет scope `api`, истёк, чужой пользователь |
| роль бота | `GET /groups/:id/members/all/:uid` | роль выше Reporter (бот сможет мержить) или ниже (не сможет комментировать) |
| служебный токен | то же, роль Maintainer+ | без него часть функций выключена |
| вебхук | создание тестового вебхука или `events: poll` | GitLab не достаёт до бота, адрес в разрешённой сети |
| образы | `docker image inspect`, `docker network inspect reviewbot-sandbox` | не собрано, нет сети песочницы |
| Docker | доступ к сокету из контейнера бота | `DOCKER_GID` не передан |
| egress | запрос к `api.anthropic.com` через прокси песочницы | прокси не поднят, хост не в `egress_allow` |
| Claude | наличие и формат токена; живой вызов только по `--live` (стоит денег) | пусто, не тот формат |

Каждая проверка печатает причину и конкретное действие, а не код ошибки.

## Что пишется на диск

- `config.yaml` — только несекретное: адрес, группы, режим событий, вебхук, образ песочницы.
  Существующий файл не перезаписывается молча: показывается diff и вопрос.
- `.env` — секреты (`GITLAB_TOKEN`, `GITLAB_SERVICE_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` или
  `ANTHROPIC_API_KEY`, `GITLAB_WEBHOOK_SECRET`), права 600, в `.gitignore`; `init` отказывается
  писать в каталог под git, если `.env` не игнорируется.
- Секреты не печатаются: ни в вывод, ни в лог, ни в итоговую сводку (только «принят»/«нет»).
- Повторный запуск `init` читает существующие значения как умолчания и не затирает чужие ключи.

## Compose

- `docker-compose.yml`: профиль `full` становится умолчанием; `docker compose up -d` поднимает
  бота и egress, сеть песочницы создаётся автоматически.
- `.env.example` со всеми переменными и комментариями.
- Образ бота и песочницы публикуются в реестр (`ghcr.io/fixcik/gitlab-review-bot`), чтобы не
  собирать локально; `docker build` остаётся для разработки.
- `DOCKER_GID` определяет `init` (на Linux читает группу сокета, на macOS не нужен).

## Страница `/setup` (только чтение)

Показывает результат `doctor` по живому конфигу: список проверок со статусом, причиной и
действием. Те же данные в `/setup/data.json`. Без полей ввода и без кнопок записи. Обновляется
по кнопке. Если сервис стартовал без токенов, `serve` не поднимает форму, а печатает
«выполните `reviewbot init`» и выходит с кодом 2.

Макет: `designs/setup-wizard/index.html` (локально, не в git).

## Безопасность

- Мастер в вебе, который принимает токены, не делаем: до настройки сервис не защищён, а токены
  попали бы в запросы, прокси и логи.
- `init` читает токены только из TTY без эха или из окружения; в `history` оболочки они не попадают.
- Проверки токенов — только чтение (`GET`); тестовый вебхук создаётся и удаляется только с
  согласия пользователя и только токеном, который для этого нужен.
- `doctor` и `/setup` не раскрывают значения секретов и не показывают, какие у токена права
  больше необходимых, кроме предупреждения «роль выше Reporter».

## План

1. `.env.example`, профиль `full` по умолчанию, образы в реестре (CI публикует по тегу).
2. `reviewbot doctor` — набор проверок как пакет `internal/doctor` с интерфейсом провайдера
   проверок (GitLab, Docker, egress); вывод в терминал и JSON.
3. `reviewbot init` поверх `doctor`: вопросы, запись `config.yaml` и `.env`, запуск compose.
4. `/setup` читает `doctor`.
5. README: быстрый старт сокращается до `reviewbot init` и `docker compose up -d`.

Каждый шаг — отдельный PR с тестами; пороги покрытия не снижаются.

## Открытые вопросы

1. Публиковать образы в `ghcr.io` (нужен релизный CI и политика тегов) или оставить сборку локально?
2. Нужен ли `init` на macOS/Windows (Docker Desktop, без `DOCKER_GID`) или только Linux-сервер?
3. Живая проверка Claude (`--live`, платный вызов) — нужна ли вообще, или достаточно формата токена?
4. Создавать ли бот-аккаунт и токены самим `init` (нужен токен администратора) — по умолчанию нет.
