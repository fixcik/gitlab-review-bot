# Автоматические метки MR

После каждого ревью бот ставит на MR метки, правила которых сработали, и (по
умолчанию) снимает **свои** метки, которые больше не подходят. Метки, поставленные
людьми, бот не снимает никогда. Правила задаются в конфиге сервиса
(`review.labels`, для всех репозиториев) и в `.reviewbot.yaml` (`labels`, для
одного репозитория).

Правило — это имя метки и условие:

- **`paths`** — glob'ы файлов: метка ставится, если MR меняет хотя бы один
  подходящий файл;
- **`when_fact`** — [факты](#факты), которые бот вычисляет сам (миграции,
  изменения API, размер MR, секреты, тесты);
- **`instruction`** — условие словами; решает модель ревью.

`paths` и `when_fact` детерминированные: результат не зависит от модели. Если у
правила несколько условий, метка ставится, когда сработало **любое** из них
(«детерминированное ИЛИ модель сказала да»).

## Примеры

### `.reviewbot.yaml`

```yaml
labels:
  rules:
    # По путям: любой изменённый файл подходит под glob.
    - name: backend
      paths: ["api/**", "src/**"]
    - name: frontend
      paths: ["web/**", "**/*.vue"]
    # По фактам бота.
    - name: db-migration
      when_fact: migrations
    - name: needs-tests
      when_fact: no_tests_changed
    - name: big-mr
      when_fact: [big_mr]
    # Решает модель.
    - name: "type::bug"
      instruction: "MR исправляет неправильное поведение (не новая функция и не рефакторинг)."
    - name: "type::feature"
      instruction: "MR добавляет новую функциональность."
    - name: "type::refactoring"
      instruction: "MR меняет структуру кода без изменения поведения."
    - name: needs-design-review
      instruction: "Меняет форму публичного API или контракты между сервисами."
    # И то и другое: метка ставится, если файл в api/contracts ИЛИ модель так решила.
    - name: contract-change
      paths: ["api/contracts/**"]
      instruction: "Меняет формат событий или сообщений, которыми обмениваются сервисы."
```

### Общие правила в `config.yaml` и их переопределение в репозитории

```yaml
# config.yaml (сервис)
review:
  labels:
    enabled: true
    remove_stale: true
    create_missing: false
    rules:
      - name: db-migration
        when_fact: migrations
      - name: security
        when_fact: lint_secret
      - name: legacy
        paths: ["legacy/**"]
```

```yaml
# .reviewbot.yaml (репозиторий)
labels:
  create_missing: true        # в этом проекте метки можно создавать на лету
  rules:
    - name: db-migration      # то же имя — заменяет правило сервиса
      paths: ["db/**"]
      when_fact: migrations
    - name: legacy            # убрать правило сервиса
      enabled: false
    - name: payments          # новое правило — добавляется после правил сервиса
      paths: ["internal/payments/**"]
```

Итоговые правила: правила сервиса по порядку (правило репозитория с тем же именем
заменяет его на месте, `enabled: false` убирает), затем новые правила
репозитория. Всего не больше 30; лишние правила репозитория игнорируются (строка в
логе). `labels.enabled: false` в репозитории выключает метки для него;
включить их, если сервис выключил (`review.labels.enabled: false`), нельзя.

## Факты

| Факт | Когда истинен | Откуда | Неизвестен, когда |
|---|---|---|---|
| `migrations` | MR добавляет или меняет миграции БД | детектор [миграций](migrations.md) по полному диффу MR | `review.migrations` / `migrations.enabled` выключены, список файлов MR не получен |
| `api_changed` | MR меняет спецификацию API: OpenAPI/Swagger, `.proto`, GraphQL (с выключенной проверкой совместимости — только OpenAPI из сводки изменений API) | обнаружение спецификаций [compat](compat.md) | проверка не выполнилась |
| `api_breaking` | детерминированная проверка нашла несовместимое изменение: oasdiff (уровень ERR), buf, graphql-inspector | [compat](compat.md); находки Claude **не** считаются | какая-то из проверок недоступна или упала, а несовместимостей не найдено |
| `big_mr` | изменённых строк больше `review.tbd.max_lines` (то же предупреждение, что в блоке «🌿 Trunk-based») | [tbd](tbd.md) | блок TBD выключен, `max_lines: 0`, размер не узнать или известен лишь как нижняя граница ниже порога |
| `lint_secret` | gitleaks нашёл секрет в коммитах MR | [lint](lint.md) | gitleaks не запускался или упал |
| `no_tests_changed` | MR меняет файлы кода (`.go`, `.py`, `.js`/`.ts`, `.php`, `.java`, `.kt`, `.rb`, `.cs`, `.rs`, …, кроме `vendor/`, `node_modules/`, `third_party/`), но ни одного теста (`*_test.go`, `test_*.py`, `*.spec.ts`, `*.test.js`, `*Test.php`, `*Tests.cs`, `*_spec.rb`, каталоги `test/`, `tests/`, `spec/`, `__tests__/`, `e2e/`, `testdata/`, `fixtures/`) | список файлов MR | список файлов MR не получен |

Факты считаются по **всему MR** (merge base … head) на каждом ревью, в том числе
инкрементальном. Факт, который не удалось вычислить, «неизвестен»: метку по нему
бот не ставит и не снимает. Других фактов (например, «нужен фича-флаг») нет: у них
нет детерминированного сигнала — для таких меток используйте `instruction`.

## Метки, которые решает модель

Если хотя бы у одного правила есть `instruction`, в промпт ревью добавляется
короткий раздел «Merge request labels» со списком таких меток и их условий (текст
из конфигурации, внутри `<label_rules>`; системный промпт говорит, что раздел
влияет только на поле `labels`), а в схему ответа — необязательный массив
`labels`, элементы которого — только имена этих меток (enum). Без правил с
`instruction` запрос к модели не меняется ни на байт.

- **Полное ревью**: модель видит весь MR; метка ставится, если модель её назвала,
  и снимается (если её ставил бот), если не назвала. Если модель вообще не вернула
  поле `labels`, это не ответ: ничего из-за этого не снимается.
- **Инкрементальное ревью**: модель видит только новые коммиты, поэтому метки по
  `instruction` только **добавляются**; снять их может лишь следующее полное ревью
  (`@bot full review`, переход Draft → Ready, force push).

С MCP метки по-прежнему приходят в итоговом JSON, отдельного инструмента нет.

## Scoped-метки (`scope::value`)

GitLab разрешает на MR только одну метку каждого scope: при установке `type::bug`
он сам снимает `type::feature`. Поэтому:

- из нескольких сработавших правил одного scope ставится **первое по порядку**
  правил (правила сервиса, затем репозитория) — располагайте их по приоритету;
- если на MR уже есть метка того же scope, поставленная **человеком**, бот свою
  не ставит (иначе GitLab снял бы метку человека);
- если метку этого scope ставил бот, она заменяется новой, и бот перестаёт
  считать старую своей.

Scope — часть до последнего `::` (`a::b::c` — scope `a::b`), как в GitLab.

## Снятие меток

Бот помнит, какие метки на MR поставил **он** (таблица `mr_labels` в базе бота).

- `remove_stale: true` (по умолчанию): своя метка снимается, когда её правило
  больше не срабатывает (или правило удалили из конфигурации). Если условие
  «неизвестно» (факт не вычислен, модель не ответила, инкрементальное ревью для
  `instruction`), метка остаётся.
- Метки людей — и те, что были на MR до бота, и добавленные вручную позже — не
  снимаются никогда, даже если правило с таким именем не срабатывает.
- Если человек снял метку, поставленную ботом, бот больше не ставит её на этом MR
  (даже если правило снова срабатывает). Если человек вернул такую метку сам, она
  считается меткой человека.
- `labels.enabled: false` или удаление всех правил: бот перестаёт трогать метки,
  уже поставленные остаются.

## Когда метки обновляются

На каждом ревью, после публикации замечаний, перед записью саммари. Бот заново
читает MR: если он к этому моменту закрыт или смержен, метки не трогаются.
Черновики (Draft) не ревьюятся автоматически, поэтому и метки на них не меняются;
поставленные раньше остаются, а переход Draft → Ready запускает полное ревью.

В саммари — одна строка, только когда есть что сказать: что поменялось в этом
ревью (и «не удалось: …», если что-то не применилось), либо, если ничего не
менялось, какие метки поставил бот:

```
🏷 Метки: +backend +db-migration −needs-design-review
🏷 Метки бота: backend, db-migration
```

(имена меток в саммари — как inline-код).

## Права и токен

Метки — метаданные MR, не содержимое репозитория: код бот по-прежнему не меняет.
Менять метки MR в GitLab может роль **Developer** и выше (Reporter умеет
ставить метки на задачи, но не на MR — [gitlab#15638](https://gitlab.com/gitlab-org/gitlab/-/issues/15638)).

1. Сначала бот пробует **свой** токен (`GITLAB_TOKEN`). У Reporter-бота это 403;
   бот запоминает отказ для проекта на час, чтобы не стучаться зря.
2. Затем — **служебный** токен (`GITLAB_SERVICE_TOKEN`, Maintainer/Owner).
   Через него же доприменяется то, что GitLab принял, но не применил (ответ 200,
   а метки не изменились).
3. Нет служебного токена и бот — Reporter: метки не ставятся, записывается
   проблема `labels_failed` («метки MR: нет прав»).

Оба клиента могут отправить в `PUT /projects/:id/merge_requests/:iid` **только**
`add_labels` / `remove_labels` — остальное (заголовок, описание, состояние,
мерж) клиент отклоняет сам ещё до запроса ([security.md](../security.md)).

Существующие метки бот проверяет через
`GET /projects/:id/labels?include_ancestor_groups=true` (метки проекта и всех его
групп, токеном бота).

## Отсутствующие метки

- `create_missing: false` (по умолчанию): метку, которой нет ни в проекте, ни в
  его группах, бот не ставит и записывает проблему `labels_failed` («метки нет в
  проекте и его группах: …»). Создайте метку (лучше на уровне группы) — со
  следующего ревью она появится.
- `create_missing: true`: бот передаёт метку как есть, GitLab создаёт её в
  проекте (для этого у токена должно быть право создавать метки — у служебного
  токена оно есть).

## Метка-исключение размера

Метку `review.big_mr.override_label` (по умолчанию `big-mr-ok`, см.
[размер MR](review.md#размер-mr)) бот не ставит никогда: иначе правило меток само
снимало бы порог `review.max_mr_lines` и блокировку `big_mr.block`. Правило с таким
именем (без учёта регистра) в `config.yaml` — ошибка конфигурации при запуске; в
`.reviewbot.yaml` сервисное значение при разборе файла неизвестно, поэтому такое
правило отбрасывается при слиянии с конфигом сервиса (предупреждение в логе один раз
на проект и метку).

## Ошибки

Ошибки меток никогда не валят ревью. Каждая — проблема проверки
`labels_failed` ([problems.md](problems.md)): блок «⚠️ Не удалось проверить» в
саммари, страница `/problems`, метрика. Метрика каждого изменения —
`reviewbot_labels_total{action="add|remove", result="ok|forbidden|missing|ignored|error"}`
([metrics.md](../metrics.md)).

Действующие правила видно в ответе на `@bot config` (строка «метки MR»).
