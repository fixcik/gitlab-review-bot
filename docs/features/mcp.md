# MCP-инструменты бота в ревью

Во время ревью модель (`claude -p` в песочнице) может вызывать инструменты самого
бота через MCP-сервер, встроенный в сервис. Две задачи:

1. **Данные по запросу.** Большие разделы промпта — список изменений API, результаты
   линтеров, подсказки по миграциям, потребители из карты системы, покрытие — в промпте
   сжимаются до одной строки («N контрактов затронуто — вызови `map_lookup`»), а
   подробности модель берёт инструментом, когда они ей нужны.
2. **Проверка замечаний на ходу.** Каждое замечание модель отправляет через
   `submit_finding`, и бот сразу проверяет его **теми же функциями**, что и при
   публикации, и отвечает, что не так и как исправить: «строка 42 не в диффе
   `src/x.php`, изменённые строки рядом: 38-40, 51-60», «critical на миграции требует
   подтверждённого `deployed_usage`, а строка `app/Order.php:42` в merge base не содержит
   `createdBy`», «дубль результата ci:phpstan на той же строке». Модель исправляет и
   отправляет снова.

Публикация не меняется: всё публикуется **в конце**, одной пачкой, через прежний
конвейер со всеми проверками (перепроверка замечаний и совместимости, дедупликация с линтерами,
правило миграций, закрытие исправленных тредов). Инструменты ничего не пишут в GitLab;
во время работы модели в MR ничего не появляется.

Включено по умолчанию (`review.mcp.enabled: true`). Пока путь MCP не проверен вживую
на всех установках, его страхует [запасной путь](#запасной-путь):
если CLI не подключился к серверу бота, ревью один раз повторяется без MCP с полным
промптом. Без MCP (выключено в сервисе или в репозитории, сервер не поднялся, запасной
путь) ревью идёт ровно как раньше: промпт байт в байт тот же (это закреплено тестом).

## Инструменты

Регистрируются только те, для которых в этом ревью есть данные. Имена для Claude Code —
`mcp__reviewbot__<имя>`, каждый разрешён в `--allowedTools` отдельно.

| Инструмент | Что отдаёт | Есть, когда |
|---|---|---|
| `diff_lines(path?)` | добавленные и комментируемые (добавленные + контекст) диапазоны строк файла в диффе MR (карта строк GitLab — та же, по которой бот потом ставит треды); без `path` — все файлы | всегда |
| `api_changes()` | полный список изменений OpenAPI/Swagger (тот же текст, что раньше был в промпте) | спецификации изменились |
| `lint_findings(path?)` | результаты линтеров и сканеров на изменённых строках; значение секретов не показывается | линтеры что-то нашли |
| `coverage(path?)` | покрытие изменённых строк по файлам: покрыто/всего, непокрытые диапазоны | есть отчёт покрытия из CI |
| `map_lookup(query)` | карта системы: затронутые MR контракты и их потребители с местами (`group/project:path:line` и путь в `/repos/...`), факты фазы B; по запросу (`POST /orders`, имя события, путь файла) — кто предоставляет и кто потребляет из всей карты | карта включена |
| `migrations()` | подсказки по миграциям (тот же раздел, что раньше в промпте) | в MR есть миграции |
| `task()` | задача(и) Jira MR, как их показывает промпт | задача найдена |
| `related_repos()` | связанные и контекстные репозитории этого ревью и где они смонтированы | есть контекст |
| `submit_finding(...)` | проверить и сохранить замечание | всегда |
| `withdraw_finding(id)` | отозвать отправленное замечание | всегда |
| `list_findings()` | что отправлено (id, путь, строка, severity, заголовок) | всегда |
| `report_progress(stage, note?)` | отметка этапа в диагностике `/runs` (в GitLab ничего) | всегда |
| `report_problem(kind, subject, detail?)` | сообщить, что модель **не смогла проверить** (инструмент не сработал, нужного кода нет в репозитории, файл слишком большой, нет доступа к связанному репозиторию, непонятная конфигурация): `kind` — `tool_failed`, `missing_dependency`, `no_access`, `too_large`, `config_unclear`, `other`; `subject` до 120 символов, `detail` до 500; не больше 5 за ревью (шестой вызов — ошибка). Записывается как проблема проверки ([problems.md](problems.md)); не для проблем кода — это замечания | `review.problems.enabled` |

Короткие и всегда полезные разделы промпта остаются как есть: задача Jira, контекстные
репозитории, память, правила команды, инструкции путей, раздел обратной совместимости
(его пункты нужно заполнить в ответе), правила миграций и фазы B карты в системном
промпте.

## Проверка `submit_finding`

Аргументы: `path`, `line`, `end_line?`, `severity` (`critical|major|minor|nit`),
`title`, `body`, `suggestion?`, `deployed_usage?` (только если в MR есть миграции).

Проверки идут в том же порядке, что после запуска, и вызывают те же функции:

| Шаг | Функция (после запуска) | Ответ инструмента |
|---|---|---|
| формат: путь внутри репозитория, без `..`; известная severity; непустые заголовок (до 300 символов) и текст (до 8000) | — (схема ответа) | `rejected` |
| нормализация | `finding.Normalize` (`finding.NormalizeReview`) | — |
| правило миграций: блокирующее замечание на файле миграции стоит, только если `deployed_usage` подтверждается строкой merge base | `migrationVerdict` (`enforceMigrations`) | `adjusted`: severity понижена до наивысшей неблокирующей, с конкретной причиной и подсказкой |
| дубль результата линтера (та же строка ±1, называет правило/инструмент; для секретов — говорит о секрете) | `lintDuplicateOf` (`dropLintDuplicates`) | `rejected` |
| уже есть открытый тред с тем же замечанием | как `publishFindings` | `rejected`: «если исправлено — в `resolved`» |
| лимит `review.max_findings` | как `finding.NormalizeReview` | `rejected`: «отзовите менее важное» |
| куда встанет: на свою строку, на соседнюю (до 3 строк), общим тредом (блокирующее вне диффа) или только в саммари | `placeFinding` (`publishFindings`) | `accepted` / `adjusted` с ближайшими изменёнными строками |

Повторная отправка с тем же путём и заголовком заменяет прежнюю версию (тот же id).
Замечание вне диффа не отклоняется — после запуска оно тоже не теряется, а попадает в
саммари или общим тредом; инструмент говорит, куда именно, и подсказывает изменённые
строки рядом.

Примеры ответов:

```json
{"status":"accepted","id":"F1","severity":"major","placement":"inline"}

{"status":"adjusted","id":"F2","severity":"minor","placement":"summary",
 "reasons":["line 42 is not in the diff of src/x.php; changed lines near it: 38-40, 51-60: this finding will only be listed in the summary, not as a thread"],
 "hint":"Anchor it on a changed line (diff_lines) to get an inline thread, or keep it as a summary note."}

{"status":"adjusted","id":"F3","severity":"major","placement":"inline",
 "reasons":["critical on the migration file migrations/V3.php blocks the merge only when it breaks the deployed code, proven by deployed_usage; the cited line app/Order.php:42 at the merge base does not contain createdBy (it reads: \"{\"): severity lowered to major"],
 "hint":"To keep critical, submit it again with deployed_usage {path, line, name}: …"}

{"status":"rejected",
 "reasons":["duplicate of the ci:phpstan result variable.undefined at src/x.php:42: the bot publishes linter results itself as their own threads"],
 "hint":"Do not report linter results again. Submit only a different or deeper problem the tool did not describe, and say what the tool missed."}
```

## Конец запуска

Финальный JSON-ответ модели — по прежней схеме. Поле `findings` может быть пустым, если
всё отправлено через `submit_finding` (так и сказано в системном промпте). Бот
объединяет принятые замечания сессии с замечаниями финального ответа (дубли по путь +
строка + заголовок отбрасываются, отправленные — первыми), сортирует по severity,
обрезает по `review.max_findings` и запускает прежний конвейер: правило миграций,
дедупликация с линтерами, перепроверка замечаний и совместимости ([verify.md](verify.md):
critical/major из `submit_finding` перепроверяются так же, как остальные; перепроверке
дают отдельную сессию только с инструментами чтения), публикация одной пачкой, закрытие
тредов. Всё проверяется ещё раз — защита в глубину.

Если CLI не подключился к серверу или конфиг не записан, ответ такого запуска не
используется: ревью повторяется без MCP ([запасной путь](#запасной-путь)). Если
инструмент отказал уже во время работы (лимит вызовов, ошибка), модель кладёт
замечания в финальный ответ, как раньше.

## Запасной путь

Путь MCP зависит от того, что CLI в песочнице действительно достучался до сервера бота
(проброс в egress, фаервол, версия CLI). Без этого модель получила бы промпт, где
большие разделы — однострочные ссылки на инструменты, которых у неё нет. Поэтому
после каждого запуска ревью с MCP бот проверяет, работали ли инструменты:

| Признак | Решение | `reason` |
|---|---|---|
| конфиг MCP не записан (`RunResult.MCPDropped`) | не работали | `config_dropped` |
| событие `system/init` потока stream-json: сервер `reviewbot` в `mcp_servers` со статусом `connected` | работали | — |
| статус есть, но не `connected` и не `pending` (`failed`, `needs-auth`, …) | не работали | `not_connected` |
| статуса нет (CLI не прислал `mcp_servers` или сервер в списке не указан) или `pending` — решает сам сервер: пришёл ли с токеном этого запуска хоть один запрос (`initialize`, `tools/list`, …) | нет запросов — не работали | `no_request` |

Если не работали:

1. Ответ запуска отбрасывается (принятые через `submit_finding` замечания тоже),
   записывается проблема `mcp_failed` («MCP-сервер бота недоступен из песочницы» или
   «конфигурация MCP не записана»), шаг `mcp: fallback` на `/runs`, в логе
   `review: mcp: the CLI did not use the bot's MCP server`.
2. Сессия MCP закрывается; до конца задачи всё идёт как с выключенным MCP (в том числе
   перепроверка — без инструментов).
3. Ревью запускается **ещё раз** без MCP: полный промпт (разделы API, линтеров, миграций,
   карты, покрытия), поле `problems` в ответе, без MCP-инструментов — тот же запрос, что
   при `review.mcp.enabled: false` (закреплено тестом с `prompt_mcp_off.golden`). Этот
   запуск считается как повтор при неверном JSON: сначала проверяется глобальный
   часовой лимит, затем запуск записывается в учёт. Если лимит не пускает — используется
   ответ первого запуска как есть (модель по системному промпту кладёт замечания в
   финальный JSON, когда инструменты недоступны).
4. **Пауза (circuit breaker).** Процесс бота 30 минут не открывает MCP для новых ревью
   (`review: mcp: skipped after a recent fallback` в логе): сломанная установка стоит
   один лишний запуск за паузу, а не по запуску на каждое ревью. Метрики:
   `reviewbot_mcp_fallbacks_total{reason}` и `reviewbot_mcp_degraded` (1, пока идёт пауза).

Формат `mcp_servers` (`[{"name":"reviewbot","status":"connected"}]`) и значения
статуса взяты из Claude Code и вживую на этой версии бота не сверены:
поэтому при отсутствии статуса решает сервер, а не CLI.

Старт сервиса MCP не роняет: если адреса для песочницы нет (`review.mcp.url` пуст и
в docker-режиме нет `sandbox.egress_proxy`) или порт `review.mcp.listen` не открылся
(занят, нет прав), в логе предупреждение `mcp: … MCP stays off`, и ревью идут без MCP.

## Безопасность

- **Отдельный слушатель.** MCP-сервер слушает `review.mcp.listen` (по умолчанию
  `:8091`), отдельно от публичного `listen`; на публичном mux его нет. Порт обязан
  отличаться (проверяется конфигом). MCP включён по умолчанию, так что порт
  открыт на всех интерфейсах, если не задать адрес (`127.0.0.1:8091` для
  `sandbox.mode: local`, IP docker-моста для бота на хосте); без токена запуска
  любой запрос получает 401, но лишний порт лучше закрыть фаерволом.
- **Токен на запуск.** Каждое ревью получает сессию со случайным 256-битным
  bearer-токеном, привязанным к (проект, MR, head SHA, запуск). Сервер хранит только
  хэш и сравнивает за постоянное время; неизвестный, закрытый или истёкший токен —
  401 до разбора запроса. Сессия закрывается сразу после работы модели (до
  публикации) и в любом случае истекает через 2 × `claude.timeout` + 5 минут.
- **Токен не утекает в логи и `/runs`.** Он передаётся CLI только в файле MCP-конфига
  (0600, во временном каталоге рядом с клоном, монтируется только на чтение в
  `/etc/reviewbot-mcp`, удаляется после запуска). Не попадает ни в командную строку
  (видна в списке процессов и в `/runs`; значение `--mcp-config` там всё равно
  заменено заглушкой), ни в переменные окружения.
  `/runs` показывает адрес сервера и список инструментов, но не токен.
- **Только данные этого MR.** Инструменты отдают результаты анализаторов этого
  запуска; `map_lookup` по всей карте показывает только этот репозиторий и
  репозитории, смонтированные в этот запуск. Пути в аргументах проверяются (внутри
  репозитория, без `..`, до 512 символов), неизвестные поля отклоняются.
- **Данные — недоверенные.** Всё, что пришло из репозитория, MR или Jira, обёрнуто в
  теги `<untrusted_…>` с той же нейтрализацией закрывающих тегов, что в промпте;
  значения секретов не показываются.
- **Ничего не пишет.** Инструменты не пишут в GitLab и репозиторий;
  `submit_finding` меняет только список замечаний сессии в памяти. Единственная
  запись в хранилище — `report_problem` (до 5 строк проблем проверки за ревью; текст
  недоверенный: метки бота, HTML и быстрые действия GitLab вычищаются, при показе —
  экранируется, см. [problems.md](problems.md)).
- **Лимиты.** Не больше `review.mcp.max_calls` вызовов на запуск (дальше — ошибка
  «лимит», замечания идут в финальный ответ); ответ инструмента до
  `review.mcp.max_response_kb` КБ (длиннее — обрезается с пометкой); тело запроса до
  1 МБ; вызов до 60 секунд; батчи JSON-RPC и SSE не поддерживаются; запросы с
  заголовком `Origin` (браузер) — 403.
- **Журнал.** Каждый вызов — шаг на `/runs` (инструмент, статус, длительность, размер,
  начало аргументов до 120 символов) и метрика
  `reviewbot_mcp_tool_calls_total{tool,status}`; вердикты `submit_finding` — строки
  `review: mcp submit_finding` в логе задачи.
- Код репозитория в песочнице не исполняется (у модели нет Bash), так что
  украсть токен из файла конфига некому; прочитать файл самой модели не даёт
  правило `Read(//etc/reviewbot-mcp/**)` в `--disallowedTools` (local-режим — путь
  временного каталога; [область чтения](../security.md#область-чтения-internalclaudereadscopego)).
  Токен умирает вместе с запуском.

## Сеть

Сеть песочницы `reviewbot-sandbox` — internal: из неё виден только контейнер `egress`.
Бот к этой сети **не подключается** (иначе из песочницы был бы виден и его публичный
HTTP-порт). Вместо этого `egress` пробрасывает **один порт на один фиксированный
адрес**: `reviewbot egress … -mcp-listen :8091 -mcp-forward <адрес MCP-слушателя бота>`.
Проброс TCP, без разбора трафика; аутентифицирует каждый запрос сам MCP-сервер.

CLI в песочнице ходит на `http://egress:8091/mcp` (адрес по умолчанию: хост из
`sandbox.egress_proxy` + порт из `review.mcp.listen`). Хост MCP добавляется в
`NO_PROXY`/`no_proxy` контейнера, чтобы CLI не отправил запрос в egress-прокси как в
HTTP-прокси.

### Всё в compose

`docker-compose.yml` уже запускает egress с `-mcp-forward ${REVIEWBOT_MCP_TARGET:-reviewbot:8091}`:
egress достаёт бота по сети по умолчанию. Настраивать ничего не нужно — значения по
умолчанию (`config.yaml` от `reviewbot init` и `deploy/config.compose.yaml` пишут их явно):

```yaml
review:
  mcp:
    enabled: true
    listen: ":8091"
```

Порт 8091 у бота **не публикуйте** (`ports:`) — он нужен только egress.

### Бот на хосте, песочница в docker (dev-режим)

```bash
REVIEWBOT_MCP_TARGET=host.docker.internal:8091 docker compose up -d egress
```

`e2e/local/run-bot.sh` (бот на хосте) так и запускает egress. Без этой переменной egress
пробрасывает на `reviewbot:8091`, которого нет: первое же ревью уйдёт в
[запасной путь](#запасной-путь) с `reason=no_request` или `not_connected`.

`host.docker.internal` в контейнере egress указывает на хост (`extra_hosts:
host-gateway`). Бот должен слушать адрес, который видно из docker-моста: например
`review.mcp.listen: "172.17.0.1:8091"` (IP `docker0`), или `":8091"` с закрытым
фаерволом снаружи. `review.mcp.url` не нужен: адрес для CLI по-прежнему
`http://egress:8091/mcp`.

### `sandbox.mode: local`

CLI запускается прямо на хосте и ходит на `http://127.0.0.1:<порт>/mcp`.

### Свой адрес

`review.mcp.url` задаёт адрес явно (например, если egress называется иначе или MCP
доступен песочнице другим путём). Без логина/пароля и query.

MCP-клиент работает в самом процессе CLI, как и запросы к API; встроенный sandbox
Claude Code (bubblewrap) больше не включается — Bash у модели нет.

## Включение и выключение

1. Обновить образ бота и egress (флаг `-mcp-forward` есть в той же версии).
2. По умолчанию включено; при необходимости `listen`, `url`, `max_calls`,
   `max_response_kb` ([configuration.md](../configuration.md#reviewmcp)).
3. Перезапустить egress и бота. В логе бота: `mcp server listening` с адресом для
   CLI; в логе egress: `mcp port forward listening`.
4. На `/runs` у запуска Claude — блок «MCP-инструменты бота», в таймлайне шаги
   `mcp: <инструмент>`, в логе `review: mcp session opened` / `closed`. Шаг
   `mcp: fallback` и рост `reviewbot_mcp_fallbacks_total` — CLI до сервера не
   достучался ([запасной путь](#запасной-путь)): проверить проброс egress.

Выключить для всего сервиса — `review.mcp.enabled: false`. Репозиторий может только
выключить инструменты: `mcp: {enabled: false}` в `.reviewbot.yaml`.
