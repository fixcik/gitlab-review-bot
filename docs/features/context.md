# Контекст из других репозиториев

Во время ревью, перепроверки (замечаний и совместимости) и ответов на вопросы Claude может читать
остальные репозитории групп из `gitlab.groups` в состоянии их главной ветки
(trunk-based: главная ветка = то, что задеплоено). Главная ветка задаётся
`gitlab.main_branch` / `gitlab.main_branches`, по умолчанию — ветка по умолчанию
проекта в GitLab. Так он находит потребителей
и поставщиков того, что меняет MR: HTTP/gRPC-клиенты, обработчики событий, таблицы и
миграции, ключи конфига, общие библиотеки. Особенно это помогает
[проверке совместимости](compat.md). Потребителей HTTP-эндпоинтов, вебхуков,
WebSocket и SSE бот заранее находит по [карте системы](sysmap.md) и даёт Claude
готовый список мест для проверки.

## Как это работает

1. Бот своим токеном (Reporter, только GET) получает список неархивных проектов групп
   и подгрупп, кэширует его на `refresh_interval`.
2. Первыми берёт [связанные репозитории](#связанные-репозитории) из `.reviewbot.yaml`.
   Из остальных пропускает пустые, крупнее `max_repo_mb`, проект самого MR и
   исключённые в `.reviewbot.yaml`; всего берёт не больше `max_repos` (по алфавиту
   пути), связанные — сверх лимита.
3. Для каждого держит снимок главной ветки **без `.git`**
   (`<data_dir>/repos/snapshots/<проект>@<sha>`), обновляет не чаще раза в
   `refresh_interval` в фоне. Старые снимки удаляются, когда ни одно ревью их не
   использует.
4. Снимки монтируются в контейнер **только на чтение** в `/repos/<группа>/<проект>`.
   Запуск ждёт готовности снимков не больше 3 минут, остальные пропускает.

Ошибка одного репозитория не ломает ревью: он пропускается, причина — в логе
(`context repositories: …`).

## Как выглядит в MR

Claude цитирует код в формате `группа/проект:путь:строка`, а бот превращает такие
ссылки в ссылки GitLab с фиксированным коммитом:

```markdown
Поле `amount` читает `billing/api:internal/client/orders.go:42`.
```

становится

```markdown
Поле `amount` читает [billing/api:internal/client/orders.go:42](https://gitlab.example.com/billing/api/-/blob/9f8e7d6c…/internal/client/orders.go#L42).
```

Ссылки работают в саммари, замечаниях, обзоре файлов, комментариях к исправленным
тредам, разделе задачи и ответах на вопросы. Ссылки на сам проект MR ведут на head
MR. Код в блоках, уже существующие ссылки и URL не трогаются.

## Настройка

```yaml
# config.yaml
gitlab:
  groups: ["backend", "platform"]   # без групп функция выключена
review:
  context:
    enabled: true
    refresh_interval: "10m"
    max_repos: 50
    max_repo_mb: 500
```

```yaml
# .reviewbot.yaml
context:
  enabled: true
  exclude: ["legacy/**", "backend/huge-monorepo"]   # glob по пути проекта
```

При старте в логе: `context repositories enabled groups=[…]` или `context
repositories off: gitlab.groups is empty`. Команда `@бот config` показывает, включён
ли контекст для MR.

## Связанные репозитории

Если у репозитория есть конкретные партнёры (фронтенд у бэкенда, мобильный клиент,
сервисы, которые он вызывает или которые вызывают его), перечислите их в
`.reviewbot.yaml`:

```yaml
# .reviewbot.yaml бэкенда
context:
  related:
    - repo: frontend/web
      note: "фронтенд, вызывает наш REST API из src/api"
    - repo: mobile/app
      note: "мобильный клиент того же API"
```

- В промпте связанные репозитории идут отдельным списком первыми, с пояснением из
  `note`, и Claude проверяет их в первую очередь: если MR меняет то, что они
  используют, он ищет использование там.
- Попадают в контекст **всегда**: сверх `max_repos` и даже если подпадают под
  `context.exclude`.
- Могут лежать **вне `gitlab.groups`**, если у бот-аккаунта есть к ним доступ на
  чтение. Такие репозитории бот находит по пути (`GET /projects/:path`) и держит их
  снимки в фоне сутки после последнего ревью, которое их запросило.
- Если репозиторий не найден, у бота нет доступа, он пустой, слишком большой или
  его снимок не удалось получить, ревью идёт без него, а в саммари MR появляется
  предупреждение:

  ```
  ⚠️ Связанные репозитории из `context.related` недоступны, ревью прошло без них:
  - `frontend/webb` — не найден или у бота нет доступа на чтение
  ```

- Проект самого MR в `related` игнорируется. До 20 записей, `note` — до 500
  символов. Работает, только когда контекст включён (непустой `gitlab.groups`).

## Безопасность и ограничения

- Снимки — только файлы дерева, без истории, remote и конфига git; права 0444;
  симлинки за пределы снимка удалены; `.claude/` и `.mcp.json` в корне не попадают.
- `.gitattributes` репозитория на снимок не действует: `export-ignore` не прячет
  файлы, `export-subst`/`ident` ничего не подставляют, `eol`/`working-tree-encoding`
  не меняют содержимое — файлы ровно как в коммите. Снимки, сделанные версией до
  этого правила, удаляются при старте.
- В docker-режиме монтирование `:ro` (а писать Claude и нечем: у него только
  `Read`, `Grep`, `Glob`); в local-режиме защита только правами 0444.
- В exec-контейнеры проверок бота снимки не монтируются.
- Код **самого** репозитория до MR (merge base) Claude видит отдельно — в `/base`,
  тоже только для чтения и с тем же пределом `max_repo_mb`
  ([security.md](../security.md#файлы)).
- Код других репозиториев для Claude — такие же недоверенные данные, как и MR.
- **Claude может прочитать и процитировать код любого проекта групп** (кроме
  исключённых в `.reviewbot.yaml` и в `review.context.exclude` сервиса) и связанных репозиториев, и этот код уходит в Anthropic. Если какой-то проект не должен
  попадать в ревью, исключите его (`context.exclude`) или вынесите из `gitlab.groups`.
- Диск: снимки занимают примерно столько же, сколько рабочие деревья проектов, плюс
  зеркала (`repos/mirrors`). См. [deploy.md](../deploy.md#размер-диска).
