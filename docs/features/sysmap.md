# Карта системы

Команда работает по trunk-based development, и каждый репозиторий деплоится сам по
себе. Самые дорогие ошибки — **между** репозиториями: бэкенд поменял ответ эндпоинта,
а фронтенд или соседний сервис об этом не знает. [Контекст](context.md) даёт Claude
прочитать остальные репозитории, но тогда на каждом ревью он ищет потребителей с нуля.

Карта системы один раз и дальше инкрементально извлекает, **кто какой контракт
предоставляет и кто его потребляет**, и на ревью бот сразу знает, где используется то,
что меняет MR.

## Что извлекается

| Протокол | Предоставляет (`provides`) | Потребляет (`consumes`) |
|---|---|---|
| `http` | обработчик маршрута REST: метод и путь | исходящий HTTP-вызов: метод и URL |
| `webhook` | эндпоинт, принимающий вебхук (и события, которые он обрабатывает) | отправка вебхука: URL и имя события |
| `ws` | сервер WebSocket: эндпоинт, события, которые он шлёт или обрабатывает | клиент: подключение, события, которые он слушает или шлёт |
| `sse` | поток Server-Sent Events: эндпоинт и имена событий | клиент (`EventSource`, потоковый `fetch`) и события, которые он слушает |

У каждой записи: репозиторий, сторона, протокол, метод (для HTTP), нормализованный
шаблон пути (`/orders/{id}`) или имя события, выражение как в коде
(`` `${ORDERS_URL}/orders/${id}` ``), «база» — откуда берётся адрес (переменная
окружения, ключ конфига, хост), файл и строка, короткая пометка.

Источники:

- **Спецификации OpenAPI/Swagger** в репозитории (те же правила поиска, что у
  [проверки совместимости](compat.md): `openapi*`/`swagger*`.yaml/yml/json или любой
  YAML/JSON с ключом `openapi:`/`swagger:` верхнего уровня). Разбираются напрямую,
  без модели: методы, пути, строки. `$ref` не раскрывается; у Swagger 2.0 к путям
  добавляется `basePath`; `servers` OpenAPI 3.x не учитываются (общие префиксы
  снимает сопоставление, см. ниже).
- **Код** `.php`, `.py`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.vue`, `.go` —
  модель `review.sysmap.model` (по умолчанию Sonnet: карта строится один раз, дальше
  перечитываются только изменённые файлы) без инструментов.
  Фреймворки команды неизвестны, поэтому промпт от них не зависит: «найди обработчики
  HTTP-маршрутов, исходящие HTTP-вызовы, входящие и исходящие вебхуки, события
  WebSocket/SSE, с номерами строк». Обёртки над HTTP-клиентом (`api.get(path)`)
  считаются вызовом в каждом месте с конкретным путём. Вызовы сторонних систем
  (OAuth- и платёжные провайдеры, объектные хранилища, мессенджеры, CRM, любой
  публичный SaaS), чей хост прямо записан в коде, модель не пропускает, а помечает:
  хост (`oauth.yandex.ru`) и короткое имя сервиса («Yandex OAuth»), см.
  [внешние зависимости](#внешние-зависимости).

Перед моделью файлы дёшево отбираются: пропускаются `vendor`, `node_modules`, `dist`,
`build`, скрытые каталоги, тесты (`tests/`, `*_test.go`, `*.spec.ts`, `test_*.py` …),
сгенерированный и минифицированный код, `docs/`, `migrations/`, `public/`, файлы
крупнее `max_file_kb` и файлы без признаков контрактов (маршруты, HTTP-клиенты,
`WebSocket`, `EventSource`, `webhook`, URL-литералы). В карту не попадают и файлы из
`sysmap.exclude` в `.reviewbot.yaml` самого репозитория (с ветки по умолчанию).

## Как строится

1. Сканер работает в фоне на снимках [контекстных репозиториев](context.md)
   (ветка по умолчанию = задеплоено) и раз в `refresh_interval` проверяет, не сменился
   ли коммит. В карту попадают те же репозитории, что и в контекст: не больше
   `review.context.max_repos`, без крупнее `max_repo_mb` и без
   `review.sysmap.exclude`. Снимки держатся, только пока файлы хэшируются и читаются
   изменённые; модель работает уже после. Репозиторий, который больше суток не
   встречается среди снимков (удалён, архивирован, вынесен из групп), удаляется из
   карты.
2. По каждому файлу хранится хэш содержимого и извлечённые записи. На новом коммите в
   модель уходят только **новые и изменённые** файлы; удалённые выбрасываются.
   Неизменившиеся репозитории не трогаются вовсе. Смена версии промпта (константа
   `CodeVersion` в коде) заставляет переизвлечь всё — это **платно**: все файлы кода
   всех репозиториев снова уходят в модель (в пределах `max_runs_per_hour`, карта
   догоняется за несколько часов), а кэш фазы B (разобранные файлы MR по хэшу)
   сбрасывается — первые ревью после обновления снова отправляют изменённые файлы MR
   в модель. Смена `max_file_kb` или `max_files_per_repo`
   заставляет заново отобрать файлы всех репозиториев на том же коммите: в модель
   уходят только файлы, которых раньше в выборке не было (например, крупные после
   увеличения `max_file_kb`); файлы, выпавшие из выборки, удаляются из карты. После
   обновления бота такой повторный отбор проходит один раз и без запусков модели,
   если настройки не менялись.
3. Файлы идут пачками (примерно до 80 тыс. символов и 25 файлов на запуск), строки
   пронумерованы, содержимое помечено как недоверенные данные. Ответ модели
   проверяется: файлы не из пачки, строки вне файла, неизвестные протоколы и записи
   без пути и события отбрасываются, пути нормализуются.
4. Запуски ограничены своим бюджетом `max_runs_per_hour` (скользящий час, переживает
   рестарт). Что не влезло, ждёт следующего прохода: репозиторий в статусе «частично».
5. Ошибка запуска — файлы ждут следующего прохода. Неразборчивый ответ — файл
   помечается и не переизвлекается, пока не изменится. Лимит Claude — проход
   останавливается.

Ревью никогда не ждут карту: они читают последнюю собранную.

## Сопоставление потребителей и провайдеров

Детерминированное, без модели и без угадывания.

**Нормализация пути.** Схема, хост и выражение базы (`${ORDERS_URL}`,
`config('services.orders.url')`) отбрасываются, query и фрагмент тоже, параметры
приводятся к одному виду:

| В коде | Шаблон | Ключ сравнения |
|---|---|---|
| `/orders/{id}`, `/orders/:id`, `/orders/<int:id>`, `` `/orders/${id}` `` | `/orders/{id}` | `/orders/{}` |
| `/orders/%s`, `/orders/{0}` | `/orders/{}` | `/orders/{}` |
| `^orders/(?P<pk>[0-9]+)/$` (Django) | `/orders/{pk}` | `/orders/{}` |
| `https://orders.internal/api/v1/orders/?page=2` | `/api/v1/orders` | `/api/v1/orders` |

Регистр и завершающий слэш при сравнении не важны.

**Правила** (по порядку):

1. **Подсказка** из `review.sysmap.hints` побеждает: если в «базе» или выражении
   вызова встречается ключ подсказки целым словом (`ORDERS_URL`, `orders.internal`),
   вызов относится к указанному репозиторию.
2. Провайдеры с тем же протоколом (HTTP и приём вебхуков сравниваются вместе),
   совместимым методом (неизвестный метод совпадает с любым) и тем же ключом пути.
3. Если таких нет — то же самое без общего префикса `/api`, `/api/vN`, `/vN` с любой
   стороны (`/api/orders` ↔ `/orders`).
4. Ровно **один** репозиторий-провайдер — вызов сопоставлен. Свой же репозиторий —
   внутренний вызов, не связь. **Ноль или несколько** — вызов **неразрешённый**, с
   выражением как в коде и списком кандидатов. Если кандидатов несколько, но маршрут
   в **коде** есть ровно у одного, а у остальных он только описан в спецификации
   OpenAPI/Swagger, провайдер — этот один: фронтенд, в котором лежит `swagger.json`
   бэкенда, не становится вторым провайдером его API. Собственный репозиторий
   вызывающего, где путь есть только в спецификации, провайдером своих же вызовов не
   считается: такой вызов уходит в другой репозиторий, а если там пути нет —
   остаётся неразрешённым (а не «своим эндпоинтом»). Если же путь есть и в коде
   вызывающего, и в другом репозитории, выигрывает **другой**: сервис редко ходит по
   сети к собственному эндпоинту. Свой репозиторий остаётся провайдером, только когда
   других кандидатов нет. Для вызовов из других репозиториев единственный провайдер
   только по спецификации (контракт пишется раньше кода) по-прежнему считается
   провайдером.

   **Спецификация в клиенте не его API.** Репозиторий, у которого в коде есть вызовы, но
   нет ни одного маршрута (фронтенд), а в файлах лежит спецификация OpenAPI/Swagger
   (`swagger.json` бэкенда), эндпоинтов не предоставляет: файл описывает чужой контракт.
   Его эндпоинты в карту не попадают — ни на `/map`, ни как кандидаты, ни как новые
   эндпоинты в MR (фаза B). Работает при сборке карты из сохранённых записей, без
   запусков модели. Репозиторий только со спецификацией (контракт пишется раньше кода)
   и сервис с маршрутами в коде свои спецификации сохраняют.

   **Моки не провайдеры.** Эндпоинты из файлов моков, заглушек, фейковых и тестовых
   серверов, фикстур и примеров в карту не попадают: каталоги `test`, `tests`,
   `__tests__`, `e2e` и любой каталог или имя файла со словом `mock(s)`, `stub(s)`,
   `fake(s)`, `fixture(s)`, `testdata`, `sandbox`, `example(s)` (слова разделяются `-`,
   `_`, `.`: `deploy/env/local/mock-api/server.js`, `src/__mocks__/`, `server.mock.js`;
   `mockingbird` или `contest` — нет; `spec/` — не тестовый каталог, там лежат
   спецификации). Фильтр работает при сборке карты из сохранённых записей, поэтому
   эндпоинты моков из старых записей исчезают после рестарта без новых запусков модели;
   новый эндпоинт мока в MR (фаза B) тоже не считается новым контрактом.
5. События WebSocket/SSE/вебхуков без пути (`es.addEventListener('order.updated')`)
   сопоставляются по имени события внутри уже связанной пары репозиториев (клиент
   подключён к `/events` этого сервера). Без пары — только если имя конкретное (с
   разделителем: `order.paid`, `chat:message`) и его шлёт ровно один репозиторий;
   общие имена (`message`, `update`) остаются неразрешёнными. Имена событий
   сравниваются без учёта регистра, а разделители `.`, `_`, `-` и пробел равнозначны
   (`chat.update` = `chat_update` = `Chat-Update`; `:` и `/` — нет); на странице имя
   показано как в коде. Вебхук, отправленный без пути (адрес — динамический
   `callback_url`), чьё имя — окончание имени события получателя по целым сегментам
   (`usage` → `llm.usage`, `oauth.exchange` → `bitrix.oauth.exchange`), сопоставляется
   с получателем («по окончанию имени события») только среди репозиториев, уже
   связанных с отправителем вызовом по пути (в любую сторону), и только если ровно у
   одного из них ровно одно такое событие с путём; иначе вызов остаётся
   неразрешённым. Модель берёт имя события буквально из кода — строковая константа
   или значение поля `event`/`type`/`status`, для вебхука с одним событием без такого
   значения — последний сегмент пути, — одинаково для отправителя и получателя
   (промпт `code-3`). Смена версии промпта переизвлекает все файлы кода всех
   репозиториев: на карте из нескольких сотен файлов это сотни запусков модели в
   пределах `max_runs_per_hour` (несколько часов) и сброс кэша фазы B.
6. **Внешний вызов.** Вызов, который модель пометила как вызов сторонней системы,
   сразу после проверки подсказок считается **внешним** — по пути и событию он не
   сопоставляется (иначе `POST https://oauth.yandex.ru/token` связался бы с чьим-то
   `POST /token`). Кроме того, внешним становится вызов, который иначе остался бы
   неразрешённым, если в его выражении или «базе» есть буквальный URL
   (`http(s)://`, `ws(s)://`) с публичным хостом — так помечаются и записи,
   извлечённые до появления пометки, без повторного сканирования. Исключение: хост,
   по которому другой вызов карты уже сопоставлен с репозиторием, — свой домен
   команды, и вызов на него остаётся неразрешённым. Внешние вызовы не входят в
   неразрешённые и не дают связей на графе.
7. **По правилу топологии** — последний шаг, только для того, что осталось
   неразрешённым (см. [Топология](#топология)).

Как сервисы узнают адреса друг друга (переменные окружения, DNS-имена k8s, конфиг),
бот не знает и не угадывает: для этого и нужны подсказки.

## Топология

Когда сервисы узнают адреса друг друга из конфигурации (`backendHost`, `LLM host`), а
провайдер отвечает вебхуками на динамический `callback_url`, по коду связь не найти.
Тогда можно заявить топологию системы в сервисном конфиге — кто кого вызывает и по
каким протоколам:

```yaml
review:
  sysmap:
    topology:
      - {from: team/shop-frontend, to: team/shop-backend, via: [http, ws]}
      - {from: team/shop-backend, to: team/shop-provider, via: [http]}
      - {from: team/shop-provider, to: team/shop-backend, via: [webhook]}
```

Вызовы из файлов, в пути которых названа сторонняя система (`bitrix`, `confluence`, `jira`,
`atlassian`, `gitlab`, `github`, `bitbucket`, `slack`, `telegram`, `sentry`, `grafana`,
`docling`), правило не связывает: это шлюз во внешнюю систему, его решает только
`review.sysmap.externals` (без него вызов остаётся неразрешённым).

Правило — последний шаг сопоставления и **никогда не перебивает** найденное в коде:
путь, событие, подсказка и внешние системы проверяются раньше. Вызов, оставшийся
неразрешённым, связывается по правилу, если для его репозитория и протокола правила
называют **ровно один** репозиторий-получатель (два разных получателя — правило не
решает, вызов остаётся неразрешённым):

- если получатель есть среди кандидатов вызова (путь есть в нескольких репозиториях),
  вызов привязывается к его эндпоинту;
- иначе связь только между репозиториями, без эндпоинта: например, вебхук провайдера с
  событием `completed`, когда у бэкенда несколько приёмников, — совпадение по имени не
  придумывается.

Такие вызовы **не неразрешённые, но и не найденные в коде**: на связи у них отдельное
число («по правилу»), они не попадают в «Требуют действия», в метрику
`reviewbot_sysmap_unresolved` и в долю неразрешённых. На графе `/map` — отдельное ребро
пунктиром с подписью «по правилу», в «Таблице связей» — своя колонка, в блоке
«Топология» — правила и сколько вызовов закрыло каждое (правило, не закрывшее ничего,
помечено «не сработало»). Правила применяются при сборке карты из сохранённых записей:
запусков модели не нужно, рестарта достаточно.

## Внешние зависимости

Хост считается внешним, только если это публичное доменное имя с точкой: адреса IP,
`localhost`, имена из одного слова (сервисы docker и k8s), суффиксы `.svc`,
`.cluster.local`, `.local`, `.internal`, `.lan`, `.localhost`, `.test`, `.example`,
`.corp`, `.home`, `.intranet` и выражения с подстановками (`https://${HOST}/…`) внешними
не бывают. Не бывают внешними и хосты домена организации — домена хоста
`gitlab.url` без первой метки (`gitlab.example.com` → `example.com`: сам
`example.com` и любые `*.example.com`; у двухметочного хоста, например
`gitlab.com`, — он сам); пометка модели на таком хосте игнорируется. Хост без схемы
в «базе» (`settings.api.url`) тоже не учитывается: это
слишком часто ключ конфига. Логин и пароль из URL (`https://user:pass@host`) в
пометку не попадают.

На `/map` такие вызовы собраны в блок «Внешние зависимости»: сервис и хост, какие
репозитории его вызывают и сколько раз, места в коде со ссылками. Если хост на самом
деле принадлежит сервису команды (например, сервис ходит к соседу по публичному
домену), добавьте подсказку `хост → проект` — подсказка проверяется раньше пометки, и
вызов станет связью:

```yaml
review:
  sysmap:
    hints:
      api.example-team.ru: backend/api
```

**Внешние системы из конфига.** Когда адрес системы в коде не виден (Bitrix24, Confluence,
Jira, GitLab, адрес — в настройках сервиса), вызов выглядит как вызов без хоста и мог бы
остаться неразрешённым или достаться правилу топологии. Такие системы объявляются в
сервисном конфиге — по файлам-вызывающим:

```yaml
review:
  sysmap:
    externals:
      - {name: Bitrix24, repo: team/shop-backend, paths: ["components/bitrix/**", "commands/BitrixAuditController.php"]}
      - {name: Jira, repo: team/shop-backend, paths: ["components/jira/**"], host: jira.example.com}
```

Вызов из файла `repo` под одним из глобов `paths` — вызов системы `name` (с `host`, если
задан): на `/map` он в ряду внешних систем, а не в неразрешённых, и правило топологии его
не связывает. Это первый шаг сопоставления — раньше подсказок; но если вызов по пути
совпал ровно с одним репозиторием-провайдером (или со своим маршрутом), побеждает
найденное в коде. Для нового вызова MR (фаза B) — так же: провайдер не ищется. Правила
применяются при сборке карты из сохранённых записей: рестарт, без запусков модели.

Ради пометки версия промпта поднята (`code-2`, затем `code-3` — буквальные имена
событий): после обновления бота все файлы кода переизвлекаются заново — постепенно,
в пределах `max_runs_per_hour`. Пока файл не
переизвлечён, работает правило с буквальным URL (п. 6 выше).

## Неразрешённые вызовы и подсказки

На странице [`/map`](../usage-and-diagnostics.md#map--карта-системы) есть список
«Требуют действия»: неразрешённые вызовы (без внешних — они в своём блоке; где, протокол, путь, выражение как в коде,
«база», причина — «нет провайдера с таким путём», «несколько провайдеров: a, b»,
«слишком общий путь» — и эндпоинты кандидатов) и вызовы, связанные с репозиторием, у
которого **нет такого эндпоинта** (подсказка ведёт в проект, где этот путь не найден,
или в проект вне карты). Чтобы связать неразрешённый вызов, добавьте подсказку по его
«базе». Проще всего — выбрать провайдера среди кандидатов прямо в списке: страница
соберёт весь блок `review.sysmap.hints` (с уже настроенными подсказками, ключи с
особыми символами — в кавычках) для копирования в конфиг. Вручную:

```yaml
# config.yaml
review:
  sysmap:
    hints:
      ORDERS_URL: backend/orders        # имя переменной окружения
      orders.internal: backend/orders   # имя хоста или выражение адреса
```

После рестарта карта пересобирается из сохранённых записей без новых запусков модели.
Подсказка не обязана совпадать с эндпоинтом: вызов связывается с репозиторием, даже
если такого пути в его карте нет.

## В ревью

Если репозиторий MR есть в карте, бот находит контракты, которые MR **затрагивает**:

- обработчики, чьи строки (в версии ветки по умолчанию) меняет дифф MR: от строки
  обработчика до конца его тела, если модель его указала, иначе до следующей записи в
  файле (не дальше 60 строк); для инкрементального ревью берётся полный дифф MR;
- эндпоинты из [сводки изменений API](compat.md) (изменённые и удалённые, не новые);
- вебхуки, которые этот репозиторий отправляет, — тогда ищутся их получатели.

Для них бот берёт из карты использования в других репозиториях и показывает в саммари
блок рядом с блоками «🌿 Trunk-based» и покрытия:

```markdown
**🔗 Затронуто в других репозиториях:**

- `POST /orders` (`backend/orders:app/routes.py:10`): `frontend/web` — 3 вызова (`frontend/web:src/api/orders.ts:12`, …); `backend/admin` — возможно, 1 вызов (`backend/admin:src/client.ts:7`)
- вебхук `POST /hooks/orders` (отправляет этот репозиторий) (`backend/orders:app/notify.py:70`): `backend/notifier` — 1 получатель (`backend/notifier:hooks.py:3`)
```

Ссылки ведут на файлы в GitLab. Длинный список сворачивается в `<details>`. **«Возможно»**
— неразрешённый вызов с тем же путём, у которого среди кандидатов есть этот
репозиторий (несколько сервисов отдают такой путь, а адрес вызова неизвестен). Если
затронутым контрактам никто не пользуется, или репозитория нет в карте, или карта
выключена — блока нет.

Тот же список (файлы и строки, пути монтирования `/repos/<группа>/<проект>/...`) Claude
получает в конце промпта (не в системном: тот одинаков для всех MR репозитория и
кэшируется) с указанием проверить эти использования **первыми**
(много мест — через субагента `code-search`) и сообщать о поломках замечанием на
изменённой строке этого репозитория со ссылкой на использование. В промпт попадают
только нормализованные пути, имена событий, проверенные пути файлов и номера строк;
выражения из кода туда не идут.

Ошибки карты никогда не ломают ревью: оно идёт без блока, причина — в логе.

## Фаза B: зависимости MR

Каждый репозиторий деплоится сам, задеплоено то, что в ветке по умолчанию, а у MR в
разных репозиториях свои задачи Jira (общими бывают только стори или эпик). Поэтому
бот дополнительно смотрит на MR со стороны **потребителя**: не зависит ли он от того,
чего ещё нет в задеплоенном соседе, и какие открытые MR в соседних репозиториях
трогают те же контракты.

> **Фаза B ничего не блокирует.** Её результаты — только блок в саммари и контекст для
> Claude. Бот не создаёт по ним тредов, не ставит маркер блокировки и не меняет строку
> о мерже. Claude получает правило: замечание, основанное на этих данных, — не выше
> `major` и никогда не `critical` (при `review.block_min_severity: critical` такое
> замечание не блокирует).

### Что MR начинает и перестаёт использовать

1. Изменённые файлы MR (полный дифф от merge base до головы, и для
   инкрементального ревью тоже) проходят тот же отбор, что и при сканировании;
   содержимое берётся из коммита головы MR (`git show`), не больше
   `deps_max_files` файлов кода. Спецификации OpenAPI разбираются без модели.
2. Извлечение — тот же промпт, схема и модель `review.sysmap.model`. Результат
   кешируется **по хэшу содержимого** и общий для всех репозиториев и веток: файл,
   который уже есть в ветке по умолчанию любого репозитория или уже разбирался в
   другом ревью, в модель не уходит. Повторное ревью того же MR обычно обходится без
   запусков.
3. Берутся записи на добавленных строках (и до двух строк выше — многострочный
   вызов), которых нет в ветке по умолчанию этого же репозитория:
   - **новый вызов** — провайдер ищется тем же сопоставлением, что и в карте
     (подсказка, путь, префикс `/api`, событие). Если такой путь не отдаёт **никто**,
     провайдер определяется по «базе»: если другие вызовы этого репозитория с той же
     базой (`ORDERS_URL`, `config('services.orders.url')`) в ветке по умолчанию
     ведут ровно в один репозиторий — это он. Несколько вариантов, нет базы, вызов в
     свой же репозиторий или во внешний API — вызов пропускается;
   - **новый эндпоинт или событие**, которое начинает предоставлять этот репозиторий;
   - **убранный вызов** — вызов из ветки по умолчанию на удалённых строках, которого
     в голове MR больше нет (или файл удалён).
   Если у репозитория MR есть правила `review.sysmap.topology`, а новый вызов идёт в
   репозиторий или по протоколу, которых в его правилах нет, в блоке появляется одна
   короткая строка «🧭 Вне заявленной архитектуры: `GET /x` → `group/project` (HTTP)»
   (до пяти вызовов, остальное — «и ещё N»). Это подсказка, не замечание и не
   блокировка; у репозитория без правил строки нет. Сами правила к новым вызовам MR не
   применяются: провайдер ищется только по коду.
4. Если у нового вызова провайдер известен, а в ветке по умолчанию провайдера такого
   метода и пути (события) нет, бот смотрит открытые MR провайдера (в его ветку по
   умолчанию): чьи добавленные строки кода или спецификации OpenAPI содержат этот путь
   (с любым синтаксисом параметров: `{id}`, `:id`, `${id}`, `<int:id>`, `%s`) или имя
   события в кавычках. Провайдер, чьё сканирование не завершено (статус «частично»),
   не проверяется: эндпоинт мог просто ещё не попасть в карту.

### Связанные MR

Для контрактов, которые MR меняет (те же, что в блоке «Затронуто», только с
потребителями-репозиториями), добавляет (кандидаты — репозитории, которые уже
вызывают этот), начинает или перестаёт использовать (провайдер), бот смотрит открытые
MR этих репозиториев и ищет тот же нормализованный путь или событие на добавленных и
удалённых строках. Найденный MR показывается с тем, что он делает, и порядком мержа,
когда он ясен:

| Этот MR | Соседний MR | Порядок |
|---|---|---|
| начинает использовать | провайдер добавляет | сначала провайдер |
| добавляет эндпоинт | потребитель начинает использовать | сначала этот MR |
| меняет эндпоинт | потребитель перестаёт использовать | сначала потребитель |
| перестаёт использовать | провайдер убирает | сначала этот MR |
| меняет / начинает использовать | меняет | неочевиден: expand/contract — сначала совместимое изменение провайдера, потом потребитель, потом удаление старого |
| начинает использовать | провайдер убирает | ⚠️ конфликт |

Если Jira настроена и у обоих MR есть ключи задач (у соседнего — из заголовка, ветки
и описания), бот отмечает общую родительскую стори («общая стори PROJ-10») или эпик
(«общий эпик PROJ-1»). Это только дополнительный признак: MR с общим эпиком, но без
общего контракта, не показывается и даже не запрашивается в Jira.

### Как выглядит

Один блок рядом с блоком «🔗 Затронуто в других репозиториях» (между маркерами
`<!-- reviewbot:sysmap-deps -->`), длинный сворачивается в `<details>`:

```markdown
**⏳ Зависит от неразвёрнутого:**

- `GET /orders/{id}/history` (`frontend/web:src/api/orders.ts:42`) нет в main `backend/orders` — добавляется в [backend/orders!12](…) (не смержен; общая стори PROJ-10): мержить после него
- `POST /orders/{id}/refund` (`frontend/web:src/api/orders.ts:57`) нет в main `backend/orders` — открытого MR, который его добавляет, не найдено

**🔗 Связанные MR:**

- [backend/billing!7](…) «feat: возвраты» — перестаёт использовать `DELETE /orders/{id}`, который меняет этот MR; общий эпик PROJ-1. Порядок: сначала backend/billing!7, потом этот MR.
```

Если сказать нечего — блока нет. Все строки из репозиториев и MR экранируются; ссылки
на MR строятся из `gitlab.url` и пути проекта. В промпт Claude (в конец, не в системный) попадают те
же факты, но только нормализованные пути, имена событий, пути проектов, номера MR и
ключи Jira (без заголовков MR и кода), с подсказкой проверить провайдера в контекстных
репозиториях или через субагента `code-search`.

Блок пересчитывается при каждом ревью (полном и инкрементальном) по полному диффу
MR; отдельных фоновых задач нет. Обновление строки пайплайна и покрытия его не
трогает.

### Стоимость фазы B

- Запуски модели для файлов MR идут из **своего** часового бюджета
  `deps_max_runs_per_hour` (по умолчанию 60), отдельного от `max_runs_per_hour`: построение
  карты и ревью не отнимают запуски друг у друга. В одном ревью — не больше
  `deps_max_runs` запусков (по умолчанию 30, ~25 файлов на запуск). Запуски пишутся в
  `sysmap_runs` с типом `deps` и видны на `/usage` с типом «Карта системы» и MR.
  Бюджет исчерпан (или `deps_max_runs_per_hour: 0`, или `max_runs_per_hour: 0`) — файлы
  не разбираются, в логе `sysmap: deps: extraction budget exhausted`, в саммари ничего.
- Запросы к GitLab — только чтение: список открытых MR соседнего репозитория (одна
  страница, `deps_max_mrs` последних) и их диффы, всего не больше
  `deps_max_api_calls` за ревью и не больше 8 соседних репозиториев. Не хватило
  лимита (или дифф какого-то открытого MR провайдера не прочитался) — строка «открытые MR
  провайдера не проверены» вместо «открытого MR, который его добавляет, не найдено».
- Jira — не больше 5 запросов задач соседних MR за ревью.
- Ошибки фазы B никогда не ломают ревью: блок просто пропадает, причина — в логе.

## Стоимость и лимиты

- Каждый запуск извлечения виден на `/usage` с типом «Карта системы» и считается на
  `/map` (запуски и условная стоимость за 30 дней, запуски за последний час из лимита).
  В `limits.global_runs_per_hour` эти запуски **не входят**: у них свой
  `max_runs_per_hour` (по умолчанию 20) на построение карты и отдельный
  `deps_max_runs_per_hour` (по умолчанию 60) на фазу B в ревью.
- Первое сканирование дороже всего: все файлы-кандидаты всех репозиториев. Например,
  50 репозиториев по 100 файлов при 20 файлах на запуск — около 250 запусков, при
  лимите 20 в час — полдня. Дальше в модель уходят только изменённые файлы.
- `max_files_per_repo` (400) и `max_file_kb` (64) ограничивают объём одного
  репозитория; сколько файлов не влезло, видно на `/map` в колонке «Пропущено».
- `max_runs_per_hour: 0` — код в модель не отправляется вовсе (и фазой B тоже), в карте
  только спецификации OpenAPI.

## Приватность

- **Код всех репозиториев групп** (кроме исключённых) отправляется в модель Anthropic
  — не только во время ревью, а в фоне, при каждом изменении ветки по умолчанию.
  Это шире, чем [контекст](context.md): там Claude читает только то, что ему нужно.
- На ревью (фаза B) в модель уходят и **изменённые файлы MR** (только отобранные
  кандидаты, не больше `deps_max_files`), если их содержимое ещё не разбиралось.
  Выключить — `review.sysmap.deps: false`.
- Исключить проекты целиком — `review.sysmap.exclude` (их записи из карты удаляются)
  или вынести их из `gitlab.groups`; отдельные файлы — `sysmap.exclude` в
  `.reviewbot.yaml` репозитория.
- Страница `/map` показывает пути файлов, эндпоинты и выражения из кода. Закройте её
  токеном (`MAP_TOKEN`), см. [security.md](../security.md).
- Содержимое файлов для модели — недоверенные данные: модель работает без
  инструментов, в пустом каталоге, ответ проверяется по схеме. Код репозиториев
  никогда не запускается.

## Ограничения

- Строки карты — из ветки по умолчанию на момент сканирования; если с тех пор ветка
  ушла вперёд, затронутые строки MR могут сдвинуться на несколько строк.
- Шлюзы, переписывающие пути сложнее префиксов `/api`, `/api/vN`, `/vN`, дают
  неразрешённые вызовы — нужны подсказки.
- gRPC, очереди сообщений и общие таблицы в карту пока не входят (их по-прежнему
  ищет Claude в [контексте](context.md)).
- Модель может пропустить или неверно классифицировать вызов; карта — подсказка для
  ревью, а не полный список. Проверяйте неразрешённые вызовы на `/map`.
- Сгенерированного JS-клиента из OpenAPI пока нет; когда появится, его вызовы можно
  будет сопоставлять точнее.
- Фаза B ищет путь в диффах соседних MR текстом: вызов, собранный конкатенацией
  (`'/orders/' + id`), не найдётся, а совпадение в несвязанной строке даст ложную
  связь; метод HTTP в диффе не проверяется. Поэтому её результат — подсказка, а не
  проверка, и ничего не блокирует.

## Настройка

```yaml
# config.yaml
gitlab:
  groups: ["backend", "frontend"]   # нужен непустой список: карта строится по контекстным репозиториям
review:
  context:
    enabled: true
  sysmap:
    enabled: true
    model: "sonnet"            # пусто — claude.light_model
    max_runs_per_hour: 20
    max_files_per_repo: 400
    max_file_kb: 64
    refresh_interval: "10m"
    exclude: ["legacy/**"]     # проекты, которые не сканировать
    hints:
      ORDERS_URL: backend/orders
    deps: true                 # фаза B: зависимости MR и связанные MR (не блокирует)
    deps_max_files: 1000
    deps_max_mrs: 10
    deps_max_api_calls: 100
    deps_max_runs: 30
    deps_max_runs_per_hour: 60
```

```yaml
# .reviewbot.yaml
sysmap:
  exclude: ["src/mocks/**", "legacy/**"]   # файлы этого репозитория, которые не сканировать
```

При старте в логе: `system map enabled …` или `system map off: it needs context
repositories …`; после каждого прохода с изменениями — `sysmap: pass done`. Все ключи —
в [configuration.md](../configuration.md#reviewsysmap).
