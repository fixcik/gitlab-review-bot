# Безопасность миграций БД

В trunk-based development код и миграции выкатываются отдельно: пока миграция
выполняется и пока новый код не раскатан полностью, трафик обслуживает
**предыдущая версия кода** — то, что задеплоено, то есть целевая ветка на момент
ответвления MR (merge base). Поэтому миграция должна быть совместима со старым
кодом. Бот находит миграции в MR, разбирает их детерминированно (без Claude),
ищет текстовым поиском в задеплоенном коде имена того, что миграция удаляет или
переименовывает, и передаёт Claude **подсказки — где смотреть**, вместе с правилами.
Решает Claude: он сам читает миграции и код, решает, есть ли проблема и насколько
она серьёзна, и пишет замечания. Своего блока в саммари и своих тредов у бота нет —
выводы только в замечаниях Claude.

Проверка обратной совместимости в целом — в [compat.md](compat.md), остальные
привычки TBD — в [tbd.md](tbd.md).

## Expand–contract

Безопасная схема изменения схемы БД:

1. **Expand** — добавить новое (таблицу, nullable-колонку, колонку с новым именем
   рядом со старой), научить код писать в оба места.
2. Бэкфилл батчами, переключение чтения на новое.
3. **Contract** — удалить старое **отдельным MR**, когда код, который его не
   использует, уже задеплоен.

Удаление колонки, которую старый код уже не трогает, — правильный шаг contract,
бот его не ругает.

## Какие миграции находит

Без настройки, по путям и по содержимому файлов, изменённых в MR (`.sql`, `.php`, `.py`):

| Фреймворк | Как распознаётся | Что анализируется |
|---|---|---|
| SQL-файлы | пути `**/migrations/**`, `**/migration/**`, `**/db/migrate/**`, … | весь файл |
| Flyway | `V<версия>__<имя>.sql`, `R__<имя>.sql` | весь файл; `U*.sql` (undo) — нет |
| goose | `-- +goose Up` | только секция Up |
| golang-migrate | `*.up.sql` | весь файл; `*.down.sql` — нет |
| sqitch | `deploy/*.sql` | весь файл; `revert/`, `verify/` — нет |
| dbmate | `-- migrate:up` | только секция up |
| Doctrine Migrations | `AbstractMigration` | только тело `up()`: `$this->addSql(...)` (в том числе heredoc), Schema API: `dropTable`, `renameTable`, `$table->dropColumn`, `renameColumn`, `changeColumn`, `addColumn`, `addIndex`, `addForeignKeyConstraint` |
| Laravel | `Illuminate\Database\…`, `Schema::…` | только тело `up()`: `Schema::drop/dropIfExists/rename/table/create`, `$table->dropColumn`, `renameColumn`, `->change()`, `->nullable(false)`, новые колонки без `nullable()`/`default()`, `index`, `unique`, `foreign`, `DB::statement` |
| Alembic | `from alembic import` | только `def upgrade*()`: `op.drop_column/drop_table/rename_table/alter_column(new_column_name=, nullable=False, type_=)`, `op.add_column(... nullable=False)` без `server_default`, `op.create_index` без `postgresql_concurrently=True`, `batch_alter_table`, `op.execute` |
| Django | `class Migration(migrations.Migration)` | список `operations`: `RemoveField`, `DeleteModel`, `RenameField`, `RenameModel`, `AlterField`, `AddField` (NOT NULL без default), `AddIndex` (а `AddIndexConcurrently` — нет), `AddConstraint`, `RunSQL` (без `reverse_sql`) |

Обратное направление (`down()`, `downgrade()`, goose Down, `*.down.sql`, Flyway
undo, sqitch revert/verify) не анализируется. В новых файлах анализируется всё, в
изменённых — только добавленные строки.

SQL разбирается по токенам: регистр, `"кавычки"` и `` `кавычки` ``, схемы
(`public.orders`), несколько выражений в строке или файле, комментарии,
строки и `$$`-тела, `IF EXISTS`, `ALTER TABLE t DROP COLUMN a, DROP COLUMN b`,
`RENAME COLUMN a TO b`, `RENAME TO b`, MySQL `MODIFY`/`CHANGE`/`RENAME TABLE`.

## Что подсказывает анализатор

Для каждой найденной операции Claude получает место (`путь:строка`), вид операции,
объект и короткое «почему стоит посмотреть». Уровней и вердиктов в подсказках нет:
серьёзность определяет Claude по [политике](#политика-severity).

| Операция | Почему смотреть | Как безопаснее (Claude предлагает в замечании) |
|---|---|---|
| удаление таблицы / колонки, переименование таблицы / колонки (`drop_table`, `drop_column`, `rename_table`, `rename_column`) | старый код может обращаться к объекту во время выкатки; к подсказке добавляются кандидаты из текстового поиска | expand–contract, удаление отдельным MR после деплоя; для переименования — новая колонка, запись в обе, бэкфилл, переключение, удаление старой |
| смена типа колонки (`alter_type`) | перезапись таблицы под ACCESS EXCLUSIVE, старый код может не понять тип | новая колонка + двойная запись + бэкфилл |
| `SET NOT NULL` на существующей колонке (`set_not_null`) | сканирование под блокировкой, вставки старого кода с NULL падают | `CHECK (col IS NOT NULL) NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL` (PG12+) |
| NOT NULL-колонка без DEFAULT (`add_column_not_null_no_default`) | падает на непустой таблице, вставки старого кода ломаются | nullable или DEFAULT → бэкфилл → NOT NULL позже |
| индекс без `CONCURRENTLY` (`create_index_not_concurrently`, только PostgreSQL) | запись в таблицу заблокирована на время построения | `CREATE INDEX CONCURRENTLY` вне транзакции |
| внешний ключ / CHECK без `NOT VALID` (`add_fk_validated`, `add_check_validated`) | проверка всех строк под блокировкой | `NOT VALID`, затем `VALIDATE CONSTRAINT` |
| UNIQUE-ограничение (`add_unique_constraint`, только PostgreSQL) | индекс строится под блокировкой записи | `CREATE UNIQUE INDEX CONCURRENTLY` → `ADD CONSTRAINT … UNIQUE USING INDEX` |
| `UPDATE`/`DELETE` без `WHERE`, `INSERT … SELECT` всей таблицы (`unbounded_dml`) | долгая транзакция в миграции схемы | батчи в отдельной data-миграции или джобе |
| `UPDATE`/`DELETE` с `WHERE` (`data_backfill`) | на большой таблице — долго | батчами вне транзакции |
| `TRUNCATE`, `LOCK TABLE`, `VACUUM FULL` / `OPTIMIZE TABLE`, `CLUSTER` | ACCESS EXCLUSIVE-блокировка | не в миграции; pg_repack |
| изменена уже существующая миграция (`modified_migration`) | применённые миграции не перезапускаются — схема разойдётся | новая миграция вместо правки |

Операции над таблицами, **созданными в этом же MR**, не подсказываются;
удаление, переименование и смена типа колонки, добавленной в этом же MR, — тоже.
Неоднозначные вызовы фреймворков (Django `AlterField`, Laravel `->change()`)
помечаются «uncertain extraction: the call may not change this».

Для `dialect: mysql` индекс без CONCURRENTLY и UNIQUE не подсказываются (online
DDL InnoDB), советы для смены типа и NOT NULL — gh-ost / pt-online-schema-change.

Claude прямо сказано, что список может быть неполным (`DO $$ … $$`, тела функций,
SQL из переменных, неподдерживаемые вызовы) и что миграции нужно читать самому.

## Текстовый поиск имён

Для удаления и переименования бот ищет имя объекта в **merge base** (задеплоенный
код) и в **head** (код MR) через `git grep -w` (только чтение, ничего не меняет в
репозитории): целое слово, с учётом регистра, в вариантах snake_case / camelCase /
PascalCase (`created_by`, `createdBy`, `CreatedBy`; для таблиц — ещё класс
сущности: `order_items` → `OrderItem`). Учитываются код (PHP, Python, Go, JS/TS,
Java, …), шаблоны, ORM-маппинги (`*.orm.xml`, `*.orm.yml`) и SQL-файлы; не
учитываются миграции, тесты, `vendor/`, `node_modules/`, дампы схемы и строки,
целиком состоящие из комментария.

Это **кандидаты**, а не вывод: в промпте до `max_usages` мест на объект с
фрагментами строк (и сколько ещё) и оговорка, что это могут быть комментарии,
несвязанные имена или мёртвый код — их нужно прочитать. Если поиск ничего не нашёл,
Claude напоминают, что объект может использоваться динамически (запросы из строк,
ORM-маппинги) — это тоже надо проверить. Общие имена (`id`, `name`, `type`,
`status`, `created_at`, `user_id`, … и короче 3 символов) помечаются как «generic
name»: в кандидаты попадают только файлы, где упоминается и сама таблица (или её
сущность).

Пределы: вывод `git grep` до 8 МБ, весь шаг — до 90 секунд; без `git grep`
(запасной путь) — до 3000 файлов и 32 МБ. При достижении предела или сбое поиска
в промпте сказано, что поиск неполный или не выполнен.

## Политика severity

Список бота — только указатель; решает Claude.

- **critical** (блокирует мерж) — **только** если удаление или переименование
  таблицы, колонки, поля или модели ломает задеплоенный код и Claude проверил это,
  прочитав код merge base (`/base/<путь>` — снимок кода до MR только для чтения): настоящий код приложения
  (не комментарий, тест, мёртвый код, миграция или однофамилец) использует объект.
  Тогда Claude обязан заполнить в замечании поле **`deployed_usage`**:
  `{path, line, name}` — строка в версии merge base файла приложения (не миграции),
  которая использует удаляемый/переименуемый объект, и имя так, как оно написано в
  этой строке. `path` — путь в репозитории (`app/models.py`), не `/base/…`.
- **major** — максимум для всего остального: блокировки и перезапись таблиц, NOT NULL,
  смена типа, массовые изменения данных, правка старой миграции, удаление или
  переименование, использование которого не удалось подтвердить или исключить.
- **minor** — мелкие риски, **nit** — стиль.

Пункты обратной совместимости для файлов миграций Claude не использует — только
замечания. Claude всегда предлагает безопасную многошаговую альтернативу.

### Принудительно в коде: проверка `deployed_usage`

Поле `deployed_usage` (необязательное) добавляется в схему ответа только когда в MR
есть миграции. После ответа Claude и до публикации бот проверяет каждое
**блокирующее** замечание к файлу миграции этого MR. Оно остаётся блокирующим, только
если выполнены все условия:

1. `deployed_usage` заполнено; `path` — относительный путь без `..`, не миграция (ни
   по путям/именам миграций, ни среди файлов миграций MR), код приложения (не тест,
   не `vendor/`); `line ≥ 1`; `name` — идентификатор (буквы, цифры, `_`, 2–128
   символов).
2. Имя — это именно тот объект, который миграция удаляет или переименовывает **на
   строках замечания** (`line`…`end_line`). Если анализатор нашёл там удаление или
   переименование, засчитывается только его объект: колонка для операции над колонкой
   (не её таблица и не класс сущности таблицы), таблица — для операции над таблицей
   (с вариантами написания: snake/camel/Pascal, класс сущности, `Order` ↔ `orders`),
   старое имя — для переименования. Если анализатор там ничего не нашёл (например,
   `DO $$ … $$`), на строках замечания должно быть слово удаления/переименования
   (`drop`, `rename`, `remove`, `DeleteModel`, без учёта регистра) и само имя целым
   словом — как написано или в snake_case (`createdBy` → `created_by`); вывод
   «таблица → класс сущности» здесь не засчитывается. Упоминание имени в другом месте
   файла миграции не засчитывается.
3. Бот читает файл в merge base сам, через git клона (а не через `/base`
   модели): строка `line` в нём
   есть, это не строка-комментарий и в ней есть имя (или вариант) целым словом.

Наличие операции в списке анализатора **не требуется**: Claude может найти удаление,
которое анализатор пропустил (например, внутри `DO $$ … $$`), — замечание должно
стоять на строке с этим удалением.

Если проверка не прошла, замечание понижается до самого высокого неблокирующего
уровня (major при `review.block_min_severity: critical` по умолчанию; minor — при
`major`), в лог пишется `review: migrations: blocking finding without confirmed
deployed-code breakage downgraded` с причиной (`reason`). Подтверждённое — строка
`review: migrations: blocking finding confirmed by deployed usage`; если Claude не
назвал место в тексте, бот дописывает «Использование в задеплоенном коде:
`путь:строка`» (для `language: en` и других — «Used by the deployed code: …»).
Пункты обратной совместимости к файлам миграций всегда превращаются в обычные
замечания того же неблокирующего уровня. За ревью читается не больше 20 файлов
merge base (с кешем по пути), проверка ограничена 20 секундами и никогда не роняет
ревью. Для замечаний не к миграциям `deployed_usage` игнорируется. Итог: мерж из-за
миграции блокирует только поломка задеплоенного кода, подтверждённая конкретной
строкой.

## Ограничения

- SQL разбирается эвристически, без полного парсера; `DO $$ … $$`, тела функций и
  процедур MySQL с `DELIMITER` не анализируются.
- SQL, собранный в коде из переменных (Django `RunSQL(sql_var)`, f-строки с
  подстановкой имён), анализируется только по литералам.
- Текстовый поиск даёт ложные кандидаты (имя в строке лога, однофамилец) и не
  находит динамически собранные имена — поэтому это только подсказки.
- Проверка `deployed_usage` построчная и текстовая: она подтверждает, что в указанной
  строке merge base есть имя удаляемого объекта, но не что это именно та таблица
  (одноимённая колонка другой таблицы пройдёт проверку). Использование, которое нельзя показать одной строкой
  (имя колонки собирается из частей, только в конфиге вне поддерживаемых файлов),
  не может быть critical — Claude ставит major.
- Удалённые файлы миграций не анализируются; переименование файла старой миграции
  и удаление строк из неё (без добавленных) считаются её изменением.
- Ruby (Rails) и Go-миграции на Go-коде (goose `.go`) пока не поддерживаются.

## Настройка

```yaml
# config.yaml
review:
  migrations:
    enabled: true
    paths: []          # доп. glob'ы файлов миграций
    exclude: []        # glob'ы, которые не считать миграциями
    dialect: postgres  # postgres | mysql
    max_files: 50
    max_usages: 5
```

```yaml
# .reviewbot.yaml (из целевой ветки)
migrations:
  enabled: true                      # false — выключить в репозитории
  paths: ["db/changes/**/*.sql"]     # добавляются к сервисным
  exclude: ["db/seeds/**"]
  dialect: mysql                     # заменяет сервисный
```

Все ключи — в [configuration.md](../configuration.md).
