# Справочник конфигурации

У бота два конфига:

| Файл | Кто владеет | Где лежит | Когда читается |
|---|---|---|---|
| `config.yaml` (конфиг сервиса) | оператор бота | на машине бота, путь в `-config` | при старте `serve` |
| `.reviewbot.yaml` (конфиг репозитория) | владельцы проекта | корень репозитория, **целевая ветка** MR | на каждой задаче |

Пример конфига сервиса: [`config.example.yaml`](../config.example.yaml), пример конфига
репозитория: [`.reviewbot.example.yaml`](../.reviewbot.example.yaml).

Общие правила:

- Длительности задаются строкой в формате Go: `"90s"`, `"10m"`, `"1h"`, `"8760h"`.
- Ключ, которого нет в файле, получает значение по умолчанию. Неизвестные ключи
  `config.yaml` игнорируются; в `.reviewbot.yaml` неизвестный ключ — ошибка (опечатка
  не должна молча выключать настройку), см. [проверку](#проверка-reviewbotyaml).
- Секреты лучше задавать переменными окружения (см. [ниже](#переменные-окружения)):
  они переопределяют значения из файла.
- Конфиг сервиса проверяется при старте; при ошибке `serve` не запускается и
  пишет в лог `invalid config: …` со списком проблем.
- Ошибка в `.reviewbot.yaml` не роняет бота: ревью этого репозитория не выполняется,
  в MR появляется одна заметка бота со **всеми** ошибками и номерами строк, на команды
  бот отвечает «Не удалось разобрать `.reviewbot.yaml` в целевой ветке …» (подробно —
  в разделе [Проверка `.reviewbot.yaml`](#проверка-reviewbotyaml)).
- По умолчанию бот ревьюит только репозитории, в целевой ветке MR которых есть
  `.reviewbot.yaml` (opt-in, [`review.require_repo_config`](#review)); как подключить
  репозиторий — [setup-gitlab.md](setup-gitlab.md#подключение-репозитория).
- Действующие для конкретного MR значения и их источник показывает команда
  `@<бот> config` (см. [команды](features/commands.md)).

Тест `internal/config/docs_sync_test.go` проверяет, что каждый ключ обоих конфигов
упомянут в этом файле.

## Конфиг сервиса (`config.yaml`)

### Корень

| Ключ | Тип | По умолчанию | Описание |
|---|---|---|---|
| `listen` | string | `":8080"` | Адрес HTTP-сервера: `/webhook`, `/usage`, `/runs`, `/healthz`, `/assets/`. |
| `data_dir` | string | `"./data"` | Каталог данных: SQLite, зеркала, клоны, снимки, диагностика. Относительный путь считается от рабочего каталога процесса. Раскладка — в [deploy.md](deploy.md#каталог-данных). |

### `gitlab`

| Ключ | Тип | По умолчанию | Описание |
|---|---|---|---|
| `gitlab.url` | string | — (обязателен) | Базовый URL GitLab, например `https://gitlab.example.com`. Завершающий `/` убирается. Env: `GITLAB_URL`. |
| `gitlab.token` | string | — (обязателен) | PAT бот-аккаунта (роль Reporter, scope `api`). Лучше через env `GITLAB_TOKEN`. По этому токену бот узнаёт своё имя: упоминание бота — `@<username>`. |
| `gitlab.webhook_secret` | string | — (обязателен при `events: webhook` и `both`) | Секрет вебхука: сравнивается с заголовком `X-Gitlab-Token`. Лучше через env `GITLAB_WEBHOOK_SECRET`. При `events: poll` не нужен. |
| `gitlab.service_token` | string | `""` | Служебный токен (Maintainer/Owner): назначение бота ревьюером, закрытие тредов, метки MR ([labels.md](features/labels.md)), синхронизация вебхуков. Необязателен. Env: `GITLAB_SERVICE_TOKEN` (или устаревшее имя `GITLAB_HOOKS_TOKEN`). См. [setup-gitlab.md](setup-gitlab.md#служебный-токен). |
| `gitlab.ca_file` | string | `""` | PEM-файл CA для внутреннего GitLab. Используется HTTP-клиентами API (бот и служебный токен) и `git fetch`/`ls-remote` бота (`http.sslCAInfo` через окружение конкретного процесса, в конфиги git не пишется). Относительный путь — от рабочего каталога процесса. |
| `gitlab.groups` | list of string | `[]` | Полные пути групп (`backend`, `platform/services`), подгруппы включаются. События из проектов вне групп отбрасываются. Пусто — принимаются события любого проекта (при старте в лог пишется предупреждение). Нужны для `sync_hooks`, опроса (`events: poll`/`both`) и контекста других репозиториев. |
| `gitlab.exclude` | list of string | `[]` | Glob'ы путей проектов (`backend/legacy-*`, `frontend/sandbox/**`), которые бот **не ревьюит**: события из вебхука и опроса игнорируются, на `@bot` не отвечает, `sync_hooks` не ставит туда вебхуки (существующие не удаляет). Без учёта регистра. Как контекст для других ревью такие проекты остаются, если их нет в `review.context.exclude`. |
| `gitlab.main_branch` | string | `""` | «Главная» (задеплоенная) ветка репозиториев групп: из неё берутся снимки соседних репозиториев для контекста, карта системы и проверка «нет в main соседа». Пусто — ветка по умолчанию каждого проекта в GitLab. Если в репозитории такой ветки нет, берётся его ветка по умолчанию (предупреждение в логе). |
| `gitlab.main_branches` | map | `{}` | Своя главная ветка для отдельных проектов: glob пути проекта → ветка (`"legacy/**": master`). Побеждает самый длинный совпавший glob (при равной длине — меньший по алфавиту); без совпадения — `gitlab.main_branch`. |
| `gitlab.webhook_url` | string | `""` | Адрес `/webhook` бота так, как его видит GitLab. Обязателен для `sync_hooks` и `reviewbot sync-hooks`. Должен быть `http(s)://…`. |
| `gitlab.sync_hooks` | bool | `false` | Держать вебхук бота в каждом проекте групп. Требует `webhook_url`, хотя бы одну группу и служебный токен. |
| `gitlab.sync_interval` | duration | `"1h"` | Как часто перепроверять вебхуки (новые проекты). Не меньше `1m`, если `sync_hooks: true`. |
| `gitlab.hook_ssl_verify` | bool | `true` | `enable_ssl_verification` у создаваемых и исправляемых вебхуков. |
| `gitlab.events` | string | `"webhook"` | Откуда бот узнаёт о событиях MR. `webhook` — GitLab шлёт вебхуки на `/webhook` (GitLab должен достучаться до бота). `poll` — бот сам опрашивает API GitLab каждые `poll_interval`: не нужны ни адрес бота, ни вебхуки, ни `GITLAB_WEBHOOK_SECRET`, `/webhook` не обслуживается. `both` — вебхук плюс опрос как страховка, одинаковые события склеиваются. Для `poll` и `both` обязателен непустой `gitlab.groups`. **Для продакшена рекомендуется `both`:** GitLab не повторяет неудачную доставку вебхука, поэтому события, пришедшие, пока бот лежал или перезапускался, при `webhook` теряются навсегда; при `both` опрос догоняет их после старта (курсоры хранятся в БД, дубли с вебхуком отбрасываются). При `webhook` бот пишет об этом предупреждение в лог при старте. См. [setup-gitlab.md](setup-gitlab.md#без-вебхуков-опрос-api) и [deploy.md](deploy.md#перезапуск-без-потерь). |
| `gitlab.poll_interval` | duration | `"5s"` | Период опроса для `events: poll` и `both`. Не меньше `5s`. Бот замечает комментарий и команду в среднем за половину периода (реакция 👀 — за ~2–3 с); цена — запросы к GitLab: один на группу за раунд и чтение обсуждений MR, обновлённых за последние 2 минуты. |

### `claude`

| Ключ | Тип | По умолчанию | Описание |
|---|---|---|---|
| `claude.model` | string | `"sonnet"` | Модель для ревью, ответов на вопросы и перепроверки совместимости. Пусто — модель по умолчанию в Claude Code. Принимаются алиасы CLI (`sonnet`, `opus`, `haiku`) и полные имена. |
| `claude.advisor_model` | string | `"opus"` | Советник для этих же запусков (серверный advisor tool Claude Code, `--advisor`): основная модель советуется с ним в сложных случаях — блокирующее замечание, несовместимое изменение, тонкие проблемы конкурентности и безопасности. Должен быть не слабее `claude.model`. Пусто — без советника. Если аккаунт или модель советника не поддерживают, бот один раз пишет предупреждение в лог (`advisor not available`) и дальше работает без него. |
| `claude.search_model` | string | `"haiku"` | Модель сабагента `code-search` (только `Read`, `Grep`, `Glob`), которому основная модель отдаёт широкий поиск: все использования символа, эндпоинта, таблицы, события, ключа конфига — в репозитории и в контекстных репозиториях. Пусто — без сабагента. |
| `claude.deep_review_model` | string | `"opus"` | Модель сабагента `deep-review` (только `Read`, `Grep`, `Glob`) — «второе мнение» на обычном маршруте ревью MR: на нетривиальном MR основная модель один раз передаёт ему изменённые файлы с диапазонами строк и черновик замечаний, он сам читает код (рабочая копия, `/base`, `/repos`) и ищет пропущенное. На лёгком маршруте (`review.routing`), в ответах в тредах и перепроверке не подключается. Запуски сабагента считаются в расходе по своей модели (`/usage`). Пусто — без сабагента. Если сабагент не отработал (модель или аккаунт не поддерживают), ревью завершается без него, бот один раз пишет предупреждение в лог и проблему `deep_review_unavailable`. |
| `claude.timeout` | duration | `"15m"` | Таймаут одного запуска Claude (ревью, вопрос, перепроверка). По таймауту контейнер принудительно удаляется. |
| `claude.light_model` | string | `"haiku"` | Лёгкая модель для коротких запусков без инструментов: извлечение правил из ответов, `запомни`, синтез правил из закрытых без правок замечаний, сжатие памяти проекта. Пусто — модель по умолчанию. |

Токен Claude задаётся только через окружение: `CLAUDE_CODE_OAUTH_TOKEN` (подписка,
`claude setup-token`) или `ANTHROPIC_API_KEY`. Без одного из них `serve` не
стартует. Задавайте одну: при обеих в `sandbox.mode: local` Claude получает только
`CLAUDE_CODE_OAUTH_TOKEN` (через файловый дескриптор), а в docker-режиме в контейнер
передаются обе и выбирает сам CLI.

### `sandbox`

| `sandbox.network` | string | `"reviewbot-sandbox"` | Docker-сеть контейнеров с Claude. Должна быть `internal` (без маршрута наружу), см. [`docker-compose.yml`](../docker-compose.yml). |
| `sandbox.egress_proxy` | string | `"http://egress:3128"` | Адрес egress-прокси изнутри сети песочницы (передаётся как `HTTPS_PROXY`). |
| `sandbox.egress_allow` | list of string | `[api.anthropic.com, statsig.anthropic.com, claude.ai, console.anthropic.com]` | Хосты, к которым прокси пропускает `CONNECT …:443`. Точное имя или `*.example.com` (только поддомены). Читается командой `reviewbot egress -config …` (в `docker-compose.yml` — из смонтированного конфига); без `-config` прокси использует значения по умолчанию. |
| `sandbox.cpus` | string | `"2"` | `docker run --cpus`. Пусто — без ограничения. |
| `sandbox.memory` | string | `"4g"` | `docker run --memory`. Пусто — без ограничения. |

Ключи `sandbox.setup_timeout` и `sandbox.allow_unsandboxed_bash` удалены (см.
[удалённые ключи](#удалённые-ключи)).

### `review`

| Ключ | Тип | По умолчанию | Описание |
|---|---|---|---|
| `review.require_repo_config` | bool | `true` | Opt-in: ревьюятся только репозитории, у которых в **целевой ветке** MR есть `.reviewbot.yaml` (пустой файл — настройки по умолчанию). Без файла авторевью молча пропускается (`reviewbot_skipped_total{reason="no_repo_config"}`), на команды и вопросы бот один раз отвечает, как подключить репозиторий (и ставит 🚫, если включены реакции); `help` работает и показывает ту же подсказку. MR, который добавляет `.reviewbot.yaml`, бот проверяет и пишет о результате заметку (ревью начнётся после мержа). `false` — ревьюятся все проекты `gitlab.groups`, как раньше. На контекстные репозитории и карту системы не влияет; вебхуки (`sync-hooks`) ставятся во все проекты групп независимо от ключа. Файл читается с кэшем на 5 минут: добавление, исправление или удаление файла действует в пределах этого времени. См. [ревью](features/review.md#какие-репозитории-ревьюятся). |
| `review.bot_mention` | string | `""` | **Устарел и игнорируется.** Упоминание бота всегда `@<username>` аккаунта из `GITLAB_TOKEN`. Если ключ задан и отличается, при старте в лог пишется предупреждение. Удалите его из конфига. |
| `review.debounce` | duration | `"90s"` | Пауза после события MR перед авторевью: серия пушей схлопывается в одно ревью. На ручные команды не влияет. |
| `review.max_diff_bytes` | int | `400000` | Предел размера диффа для Claude. Больше — бот берёт самые изменённые файлы, которые помещаются, и пишет в саммари «⚠️ Изменения слишком большие…». Действует и для ревью сверх `review.max_mr_lines` по `review force` / метке. |
| `review.max_mr_lines` | int | `2000` | Жёсткий порог размера: если в проверяемом диапазоне (полное ревью — весь MR, инкрементальное — новые коммиты) больше стольких изменённых строк (добавлено + удалено, без файлов из `ignore`; счёт тот же, что у `review.tbd.max_lines`), Claude **не запускается вообще**, в саммари — блок «📦 MR слишком большой для ревью». `0` — без порога. Ставьте не ниже `review.tbd.max_lines`: иначе MR, по которым TBD-блок ещё не предупреждает, уже не будут ревьюиться (не ошибка конфига). См. [ревью](features/review.md#размер-mr). |
| `review.skip_trivial_increments` | bool | `true` | Автоматическое **инкрементальное** ревью новых коммитов, которые меняют только пробелы/форматирование, комментарии или документацию (`*.md`, `*.rst`, `*.adoc`), Claude не запускает: бот сдвигает отметку проверенного коммита, оставляет треды как есть, пишет в саммари «ℹ️ Инкремент … без значимых изменений (только форматирование/комментарии) — ревью не требуется» и выполняет только gitleaks, проверку TODO без задачи и чтение отчётов CI-линтеров (`lint.ci`). Полное ревью и ручное `review` не пропускаются никогда (ручной командой такой пуш можно проверить). Добавленные, удалённые, переименованные и бинарные файлы, смена прав и файлы неизвестного типа — не «тривиальны»; комментарии-директивы и аннотации (`//go:build`, `# type:`, `@IsGranted`, `eslint-disable`…), строки Python не-докстринги и всё, что лексер не различает уверенно (heredoc, многострочные строки, cgo, HTML со `<script>`), — код. `reviewbot_skipped_total{reason="trivial_increment"}`. См. [ревью](features/review.md#тривиальные-пуши). |
| `review.default_language` | string | `"ru"` | Язык текста ревью по умолчанию: `ru`, `en`, `de`, `uk`, `es`, `fr` или любое название языка. Репозиторий переопределяет ключом `language`. |
| `review.default_ignore` | list of string | `["**/*.lock", "**/go.sum", "**/package-lock.json", "**/*.min.js", "vendor/**", "node_modules/**"]` | Glob'ы файлов, которые не ревьюятся. К ним добавляется `ignore` из `.reviewbot.yaml`. |
| `review.max_findings` | int | `30` | Не больше стольких замечаний Claude за одно ревью (сначала самые серьёзные). `0` — без ограничения. |
| `review.block_min_severity` | string | `"critical"` | Замечания этого уровня и выше блокируют мерж: `critical`, `major`, `minor` или `nit`. См. [ревью](features/review.md#блокировка-мержа). |
| `review.assign_reviewer` | bool | `true` | Добавлять бота в ревьюеры MR перед ревью. Работает только со служебным токеном. |
| `review.compat_check` | bool | `true` | Проверка обратной совместимости во всех репозиториях. См. [compat.md](features/compat.md). |
| `review.compat_timeout` | duration | `"3m"` | Таймаут одного запуска инструмента проверки совместимости. |
| `review.diagram` | bool | `true` | Mermaid-схема изменений в саммари. Репозиторий может выключить у себя (`diagram: false`). |
| `review.description_summary` | bool | `false` | Саммари изменений в **описании** MR («Саммари от ревью-бота»: 1–2 предложения и список по группам — новое, исправления, рефакторинг, тесты, документация, прочее), на языке ревью; бот обновляет только свой блок между маркерами, текст автора не трогает ([саммари в описании](features/description-summary.md)). Выключено по умолчанию: бот пишет в чужие описания (нужны права Developer или служебный токен). Репозиторий может выключить у себя (`description_summary: false`). |
| `review.parallel_analyzers` | bool | `true` | Быстрые проверки перед запуском Claude (выгрузка `/base`, совместимость и «Изменения API», gitleaks/TODO/CI-линтеры, Jira, контекстные репозитории, покрытие, карта системы, миграции) выполняются **одновременно** (до 4 сразу) с учётом зависимостей: карта системы ждёт совместимость и контекстные репозитории, её фаза B — ещё и Jira. Результат и порядок проблем в саммари те же, что при последовательном выполнении. `false` — по очереди, как раньше (если что-то ведёт себя иначе при параллельном запуске). См. [ревью](features/review.md#скорость-ревью). |

### `queue`

Очередь задач: что переживает перезапуск и как бот останавливается. Только конфиг сервиса. Подробно —
[deploy.md](deploy.md#перезапуск-без-потерь).

Все задачи очереди хранятся в SQLite и после перезапуска выполняются снова: авторевью (одно на MR, с прежним
debounce и отсрочкой по лимиту) и все остальные — команды (`review`, `full review`, `check`, `pause`, `config`,
правила, память…), вопросы боту, ответы в тредах, обновления сводки, разбор пайплайнов — в прежнем порядке.
Задача, которую остановка прервала посреди работы, повторяется, если её итоговый ответ ещё не опубликован; если ответ
уже есть, повтор пропускается (иначе ответ появился бы дважды).

| Ключ | Тип | По умолчанию | Описание |
|---|---|---|---|
| `queue` | object | | Очередь задач. |
| `queue.shutdown_grace` | duration | `"5m"` | Сколько при остановке (SIGTERM/SIGINT) ждать задачи, которые уже выполняются: новые задачи не запускаются, вебхуки и опрос продолжают приниматься и сохраняются в очередь, выполняющиеся ревью и ответы дорабатывают (токены Claude не теряются). По истечении — прерываются и повторяются после старта. Повторный сигнал прерывает сразу. `0` — прерывать сразу (прежнее поведение), не больше `1h`. **Таймаут остановки контейнера должен быть больше** (`stop_grace_period` в docker compose, `terminationGracePeriodSeconds` в Kubernetes; у Docker по умолчанию всего 10 с), иначе процесс убьют посреди ожидания. |
| `queue.manual_max_age` | duration | `"6h"` | Задачи, кроме авторевью (команды, вопросы, ответы в тредах, обновления, пайплайны), поставленные в очередь раньше этого срока, после перезапуска не выполняются, а отбрасываются (строка в логе, метрика `reviewbot_queue_restored_total{result="expired"}`): ответ через полдня уже не нужен. Больше `0`. |

## Конфиг репозитория (`.reviewbot.yaml`)

Файл читается из **целевой ветки** MR: автор MR не может в самом MR поменять
инструкции, команды или выключить проверки для своего изменения. Пустой файл —
действуют настройки сервиса. Само наличие файла подключает репозиторий к ревью
(при `review.require_repo_config: true`, по умолчанию); без файла репозиторий не
ревьюится. При `review.require_repo_config: false` отсутствие файла означает
настройки сервиса.

Подсказки и проверка ключей в редакторе — JSON Schema
[`docs/reviewbot.schema.json`](reviewbot.schema.json). Первая строка файла:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/fixcik/gitlab-review-bot/main/docs/reviewbot.schema.json
```

Её понимают VS Code (расширение Red Hat YAML), JetBrains IDE и всё, что работает
через yaml-language-server. Если редактор не видит GitHub, положите схему рядом
(например в `.gitlab/reviewbot.schema.json`) и укажите относительный путь:
`$schema=./.gitlab/reviewbot.schema.json`. Схема генерируется из структур кода
(`UPDATE_SCHEMA=1 go test ./internal/config -run TestRepoSchemaUpToDate`); тест
`TestRepoSchemaUpToDate` не даёт ей разойтись с кодом. Схема знает ключи, типы и
закрытые списки значений (`lint.disable`, `lint.ci[].format`, `migrations.dialect`,
`labels.rules[].when_fact`, уровни серьёзности); остальные проверки (glob'ы, диапазоны,
лимиты, удалённые ключи с объяснением) делает только бот и `validate-repo-config`.

### Проверка `.reviewbot.yaml`

Бот проверяет файл строго и сообщает **все** ошибки сразу, с номерами строк:

- синтаксис YAML (тогда остальное проверить нельзя);
- неизвестные ключи — с подсказкой ближайшего известного (`auto_reviw: unknown key
  (did you mean "auto_review"?)`), на любом уровне вложенности (`lint.ci[0].jb`);
- [удалённые ключи](#удалённые-ключи) — со своим объяснением (`setup`, `tools`,
  `compat.commands`, `lint.custom`, `lint.semgrep_configs`);
- типы значений (строка вместо списка и т.п.) — по одной ошибке на раздел;
- значения (`tbd.max_lines must be >= 0`, неверный glob, неизвестный инструмент в
  `lint.disable`, лимиты `lint.ci`, `todo.keywords` и т.д.) — по одной ошибке на раздел;
- повторяющиеся ключи, больше одного YAML-документа, файл больше 256 КиБ.

**Невалидный файл в целевой ветке** — ревью не выполняется, пока его не исправят:

- в MR появляется **одна** заметка бота (маркер `<!-- reviewbot:config-error state=error -->`)
  со списком ошибок (до 20) и подсказкой, как исправить; при следующих событиях она
  обновляется на месте, а не дублируется. Бот не правит файл и не открывает MR с
  исправлением;
- на `/problems` — проблема `repo_config_invalid` (одна на проект, с текстом ошибок;
  см. [проблемы](features/problems.md));
- авторевью пропускается (`reviewbot_skipped_total{reason="repo_config_invalid"}`); на
  `review`, вопросы и команды бот отвечает в треде «Не удалось разобрать
  `.reviewbot.yaml` в целевой ветке `main`: line 3: auto_reviw: unknown key … (и ещё 2).
  Ревью не выполняется; все ошибки и как исправить — в заметке бота в этом MR.»
  (🚫 на команде, если включены реакции). `help`, `pause`/`resume`, `ignore`,
  `resolve all` работают; `config` отвечает тем же сообщением.
- Когда исправленный файл попал в целевую ветку (с учётом кэша — до 5 минут), следующее
  ревью идёт как обычно, а заметка меняется на «✅ Конфиг исправлен: `.reviewbot.yaml`
  в `main` валиден, ревью выполняется» (`state=ok`; заметка остаётся для истории).

**MR, который добавляет или меняет `.reviewbot.yaml`**: бот проверяет и версию из MR
(HEAD) и пишет результат в ту же заметку. Мерж она не блокирует.

| Ситуация | Что делает бот |
|---|---|
| Репозиторий подключён, в MR конфиг с ошибками | ревью идёт по конфигу целевой ветки; заметка «⚠️ `.reviewbot.yaml` в этом MR невалиден» с ошибками и строка об этом вверху саммари |
| Репозиторий подключён, в MR исправленный конфиг (в целевой ветке — с ошибками) | ревью нет; в заметке ошибки целевой ветки и «✅ В этом MR `.reviewbot.yaml` исправлен — ревью заработает после его мержа» |
| Репозиторий не подключён, MR добавляет конфиг с ошибками | ревью нет; заметка с ошибками и «Репозиторий подключится к ревью после мержа валидного `.reviewbot.yaml`» |
| Репозиторий не подключён, MR добавляет валидный конфиг | ревью нет; заметка «✅ Новый `.reviewbot.yaml` валиден — ревью этого репозитория начнётся после мержа MR» |
| Ошибки в MR исправлены следующим пушем | та же заметка меняется на «✅ Новый `.reviewbot.yaml` валиден» |
| MR не трогает конфиг, всё валидно | заметки нет |

Тексты из файла (ключи, значения) в заметке экранируются: упоминания, ссылки и
HTML-комментарии из MR в заметку не проходят.

#### Проверить локально и в CI

```sh
reviewbot validate-repo-config                    # ./.reviewbot.yaml
reviewbot validate-repo-config path/to/.reviewbot.yaml
go run github.com/fixcik/gitlab-review-bot/cmd/reviewbot@latest validate-repo-config
docker run --rm -v "$PWD:/w" -w /w reviewbot:dev reviewbot validate-repo-config
```

Проверка та же, что у бота (без `config.yaml`, токенов и сети). Вывод — по строке на
ошибку: `.reviewbot.yaml:4: auto_reviw: unknown key (did you mean "auto_review"?)`.
Код выхода: `0` — файл валиден (`.reviewbot.yaml: ok`), `1` — есть ошибки, `2` — файл
не прочитан или неверные аргументы. Пример job'а для CI:

```yaml
reviewbot-config:
  image: reviewbot:dev        # образ бота из вашего реестра
  script: [reviewbot validate-repo-config]
  rules:
    - changes: [.reviewbot.yaml]
```

### Что репозиторий может, а что нет

| Ключи | Что может репозиторий |
|---|---|
| `limits.*` | только ужесточить (меньше лимит, больше cooldown) |
| `max_mr_lines`, `big_mr.block` | только ужесточить (меньше порог; включить блокировку) |
| модели (`routing`, любые `*model*`) | **нельзя**: модели и выбор модели по риску задаются только в сервисном конфиге (`claude.*`, `review.routing`); секция `routing` в `.reviewbot.yaml` — ошибка конфига |
| `compat.enabled`, `diagram`, `memory.enabled`, `learn.enabled`, `context.enabled`, `lint.enabled`, `lint.disable`, `migrations.enabled`, `mcp.enabled`, `problems.summary`, `verify.enabled`, `labels.enabled`, `todo.enabled`, `reactions.enabled`, `ci.enabled` | только выключить то, что включено в сервисе; включить выключенное в сервисе нельзя |
| `todo.blocking` | только ужесточить: `true` делает замечания «TODO без задачи» блокирующими, `false` не отменяет `review.todo.blocking: true` |
| `lint.disable: [gitleaks]`, `lint.enabled: false` | gitleaks остаётся включённым, пока сервис не разрешил `review.lint.allow_disable_secrets` |
| `ignore`, `path_instructions`, `compat.*` (пути спецификаций), `todo.ignore`, `ci.ignore_jobs` | дополнить списки сервиса |
| `lint.ci` | задать свои (сервис их не задаёт; `review.lint.enabled: false` выключает и их) |
| `language`, `instructions`, `max_files`, `jira.project_keys`, `jira.title_prompt`, `jira.title_language`, `enabled`, `auto_review`, `labels.remove_stale`, `labels.create_missing`, `todo.keywords`, `todo.severity` | задать своё значение |
| `labels.rules` | дополнить правила сервиса; правило с тем же `name` заменяет правило сервиса, `enabled: false` — убирает его |

Что модель может делать, репозиторий не меняет: у неё всегда только `Read`, `Grep` и
`Glob` в пределах каталогов запуска ([security.md](security.md#права-claude)). В
песочнице выполняются лишь проверки бота (gitleaks, проверки совместимости); своих
команд репозиторий добавить не может (`compat.commands`, `lint.custom` удалены).

instructions: |
  Обращай внимание на обработку ошибок и закрытие ресурсов.

path_instructions:
  - path: "migrations/**"
    instructions: "Проверяй обратимость и блокировки таблиц"

  project_keys: ["PAY"]
learn:
  enabled: true
memory:
  enabled: true
context:
  enabled: true
  exclude: ["legacy/**"]
compat:
  enabled: true
  openapi: ["contracts/*.yml"]
lint:
  ci:
    - job: phpstan
      report: codequality
todo:
  keywords: [TODO, FIXME]
  ignore: ["legacy/**"]
migrations:
  paths: ["db/changes/**/*.sql"]
  dialect: postgres

  rules:
    - name: backend
      paths: ["api/**", "src/**"]

## Удалённые ключи

Модель больше не запускает команд: у Claude только `Read`, `Grep` и `Glob`, код до
MR — в `/base`, покрытие — в промпте ([security.md](security.md#что-убрано-вместе-с-bash)).
Ключи, которые управляли командами, удалены. Конфиг, где они ещё есть (с любым
значением, даже пустым), **не загружается** с ошибкой
`<ключ>: removed: the review model no longer runs commands; see docs/security.md`:

| Где | Ключ | Что делать |
|---|---|---|
| `config.yaml` | `sandbox.setup_timeout` | удалить |
| `config.yaml` | `sandbox.allow_unsandboxed_bash` | удалить: встроенной изоляции Bash больше нет, Bash тоже |
| `config.yaml` | `review.default_tools` | удалить |
| `.reviewbot.yaml` | `setup` | удалить: подготовка окружения не нужна, модель ничего не собирает |
| `.reviewbot.yaml` | `tools` | удалить: что раньше проверяли командами (`go vet`, тесты), проверяет CI; результаты линтеров из CI (`lint.ci`) и покрытие модель получает готовыми |
| `.reviewbot.yaml` | `routing` | удалить: модели выбирает только сервис (`claude.*`, `review.routing`). Ошибка — `routing: removed: models are chosen only in the service config (claude.*, review.routing); see docs/configuration.md` |
| `.reviewbot.yaml` | `compat.commands` | удалить: бот не запускает код репозитория; перенесите проверку в CI. Ошибка — `compat.commands: removed: the bot no longer runs repository commands (code from the MR never executes); see docs/security.md` |

Сервис с таким `config.yaml` не стартует (`serve`, `egress`, `sync-hooks`). Для
репозитория ошибка — как у любого неверного `.reviewbot.yaml`
([проверка](#проверка-reviewbotyaml)): ревью нет, в MR — заметка со всеми ошибками,
каждый удалённый ключ — отдельной строкой со своим номером строки и объяснением
(`line 4: tools: removed: the review model no longer runs commands; see docs/security.md`),
пока ключи не уберут из целевой ветки. `reviewbot validate-repo-config` показывает то же.
Ключ `review.lint.tools` к этому не относится; `lint.custom` и другие ключи бывших
линтеров удалены со своей ошибкой (`removed: linters now come from CI reports…`, см.
[`lint`](#lint)).
